# Changelog

## Unreleased

### Breaking Changes

- Decision Gate is now part of Discuss Work (`skills/discuss-work`), and it now runs before building: on a task that builds or changes behavior, the agent first sends one message with what it will do, where it stops, and the choices that are yours, each with its default, then waits. "Go" accepts every default, and a correction changes only the line it names; a question needs no agreement, an exactly specified change or a run nobody can answer counts as one, and you can ask to skip the wait. The choices are kept in one decision list through the task (`sources/decisions.md` beside a Working Record, where only the choices you answered become Decisions), self-review checks the work against it, and the final report shows only choices you have not seen. Workflow's Asking The User reference is folded into Discuss Work and removed. Update links and scripts that name `skills/decision-gate` or `skills/workflow/references/asking-the-user.md`.
- Evaluate Skill is renamed Evaluate Behavior (`/evaluate-skill` becomes `/evaluate-behavior`), and its subject is now any declared part of the agent's setup, such as its skills, instruction files, model, or host extensions and settings. Update links, commands and scripts that name `skills/evaluate-skill`; the evaluator script is still `scripts/skill-eval.mjs`, and definitions stay under `.skill-eval/`.
- Review Artifact is merged into Review Work, and `/review-artifact` is removed: use `/review-work`, which now reviews code and other finished work as well as documents that guide later work (specs, plans, designs, decision records, handoffs and skills). Its rules, review budget and judgments are unchanged; each kind keeps its own sources, job checks and lenses, and one reviewer contract and one adjudication reference cover both.
- Evaluate Behavior definitions are schema 2, and schema 1 files no longer load: rewrite them in the new shape. A group is now a task (prompt, fixture, tools, expectations) plus a `configuration` (host, model, the skill under test, and optionally Freeflow and a runtime); `arms.baseline` and `arms.candidate` each overlay it, and `component` names the only paths where the two may differ, such as `subject.source` or `model.thinking`. A group whose arms differ anywhere else, or that declares a difference that is not there, is refused before anything runs, and `component: []` runs the same configuration twice to measure run-to-run variation. `extends` shares one configuration file across groups. The authoring reference shows the full shape.
- `skill-eval run` refuses, before anything starts, a run whose inputs are not committed: the definition files, the fixture, runtime bundles, and working-tree skills and context must match the repository's commit, which the result then records. Add `--dry-run` to run anyway; the result is marked as a dry run and supports no claim. A configuration's `host.version`, when declared, must match the installed `pi --version`.
- Discuss and Agree Work are merged into one skill, Discuss Work (`skills/discuss-work`), with its own command `/discuss-work`. `skills/discuss`, `skills/agree-work` and the `/discuss` command are removed, with no alias: update links, scripts and commands that name them.
- The Action Selection skill is removed. Its description matched almost every search or command and its body was almost never opened; its one rule that reached the work, keeping tool output small and saying when it was cut, is now in the Working Method on every host, and the rest repeated the Working Method or other skills. The `/action-selection` command is gone. No alias replaces it.
- Bypass is no longer a skill, and `/bypass` is removed with no alias. Discuss Work now says what it did: when you explicitly ask to skip an optional step, such as waiting for the agreement, a plan, a review or a record, the agent skips only that, takes its defaults and reports them, still asks before a hard-to-reverse choice, and changes no authority, checkpoint you selected, or claim. When that skip must outlast the conversation and a Working Record exists, the agent records it in the Work agreement.
- The Commit Work, Finish Branch, Release Work and Launch Work skills are removed; their methods are in Deliver Work. Their commands `/commit-work`, `/finish-branch`, `/release-work` and `/launch-work` are removed with no alias: use `/deliver-work`.
- The Design for Depth, Simplify Code, Diagnose Failure and Migration Work skills are removed; their methods are references in Execute Work. Execute Work's Execute Work Edges and Domain Skill Composition references and Design for Depth's Implementation Decisions reference are removed too: what they held that nothing else did is now in Execute Work, its design reference and Track Work. Their commands `/simplify-code`, `/migration-work` and `/diagnose-failure` are removed with no alias: use `/execute-work`.
- The Handoff skill and its `/handoff` command are removed with no alias; writing a handoff is now part of Track Work (`skills/track-work/references/handoff.md`), opened when work pauses or passes to another session or person. Update links, scripts and commands that name `skills/handoff`.
- The Write Spec and Write Plan skills and their `/write-spec` and `/write-plan` commands are removed with no alias; specs, plans and decision records are now written with Write Docs (`/write-docs`). Update links, scripts and commands that name `skills/write-spec` or `skills/write-plan`, or their `spec-shapes`, `plan-shapes` and `artifact-standards` references.

### Added

- On Pi, Freeflow pushes a few lines of guidance at the tool call that needs them: Deliver Work's commit essentials on a `git commit` result (with a reminder of Write Skill's loss check when the commit holds instruction text), diagnose's key lines when the same test command fails a second time, and a reminder to run Execute Work's self-review when a test passes after a change. `toolExecution.guidanceNotices: false` turns them off.
- Skills now come with scripts that put the facts a decision needs in front of the agent. Execute Work's `touch-map.mjs` answers what a change touches (entry points, readers, writers, scheduled code, covering tests and the developer docs covering each file, each block saying what it did not search), and `self-review.mjs` writes one report before the agent reports a change: status, diff stat, every changed existing test or fixture with its hunk, each new test and whether it fails on the base, and whether each requirement's check ran after the last edit.
- Discuss Work's `choices.mjs` checks the decision list and renders the agreement, the hand-over's unseen choices, and a catch-up after an unattended run (defaults taken, choices waiting, what ran).
- Deliver Work's `delivery-state.mjs` reports branch, upstream, uncommitted work, an operation in progress, worktrees (flagging the session's own), the latest tag, version and changelog in one read-only call; `commit-state.mjs` tells your changes from pre-existing staged work; `release-preflight.mjs` and `push-route.mjs` check a release and a simple push locally without performing them.
- Review Work's `review-packet.mjs` prefills a reviewer's brief, names the review gate's triggers and the round budget, and runs `check-brief.mjs`. Write Docs' `plan-lint.mjs` lists Plan steps that name no check, and `artifact-check.mjs` checks a Spec, Plan or decision record's status and source trail.
- Track Work's `working-record.mjs view recover` gives, in one call after context loss, the resume view, each defining artifact and Recovery source with its trigger and whether it resolves, and where live Git state disagrees with the record; `validate` now warns about Material updates pointers (files, commits) that do not resolve, and `--strict` fails on those an Evidence or Result line names.
- `skill-author compare` treats reasons (because, so that, otherwise, why) as protected like rules, and `--all-units` needs a verdict for every unmatched unit in a substantial revision. Verify Work's `test-changes.mjs --new` lists added test files.
- Evaluate Behavior body groups on Pi can close and resume the subject's session between turns: `input.resume_before` names the turns to resume before, with `runtime.session` on.
- `skill-eval check-tasks` lists, for every group, what the task's copy lacks against the setting it came from: Git history (a workspace is never a repository), ignored files the fixture holds (a clone lacks them) or the task names (such as `.env`), and tools or network the task asks for but the subject lacks, with each arm's tools and network. It reports these without refusing, and still calls no model.
- Evaluate Behavior scans every run's transcript and flags reads outside the workspace and declared resources, attempts to reach an external network target, reads of instruction files (`CLAUDE.md`, `AGENTS.md`, `.claude/`) outside the workspace, and hidden-test or reference-solution text in the subject's answer or files. A flagged run stays in the results but is held out of every count and decision, and stops a pilot, until you clear it with `skill-eval clear <result> --variant <arm> --flag <id> --reason <text>`, which records your reason beside the run and recounts every aggregate that lists it.
- Evaluate Behavior configurations can declare `network`: `"none"` seals the subject, so its bash, declared commands and command graders all run confined with no network and none of your files, including the provider login on disk, and a group that would run declared commands or graders on the host is refused; `"host"` allows them on the host on purpose. Each run records `sealing` (what its code could reach and where each part ran), the plan line names arms whose code would run on the host, and a declared command no longer receives the path of Pi's login directory or a login variable.
- Evaluate Behavior checks that each run shows a model at work before grading it: a run the host reported complete but with no assistant message, zero tokens, or no answer and nothing written (as after a failed login) is reported `invalid` with its reasons, never as a fail; it counts in no comparison, metric summary or decision, and it stops a pilot. Tokens are the signal rather than cost, which is zero for real work on a model with no configured price.
- Evaluate Behavior groups can run any number of named arms against a reference arm (`reference`, default `baseline`), or a single arm that measures one setup with nothing to compare (pass^k, metrics and judged scores, no comparison claim). Two-arm groups keep working unchanged.
- A suite can declare a `decision` rule before it runs (the measure, the two arms, the direction, alpha and the minimum cases): the aggregate then reports "beats", "worse" or "no difference shown" from an exact sign test over cases, and only then says "beats". A rule's `trials` schedule adds trials only to cases still undecided, up to a maximum.
- Every run records metrics (duration, turns, tool calls and errors, tokens, cost, cache hit rate), and an aggregate summarizes them per arm with paired differences against the reference; a decision can use them as its measure.
- Evaluate Behavior run metrics on Pi add `peakContext`, the largest single request a run sent (input plus cache reads plus cache writes), and `skillReads` and `skillReadTokens`, every read of a declared skill's files or of the loaded Freeflow package's skills and prompts, re-reads included, with tokens estimated from bytes. Aggregates report them per arm with paired differences, and a decision can use them as its measure.
- Judged evaluation: a group's `rubric` is answered by declared `judges` for each run alone, blind to its arm (`skill-eval review --rubric`), combined by a declared rule, stored apart from run and grade files, with agreement between judges and calibration against hand labels (`--calibrate`). `--swap-sample` checks order on a sample of groups.
- Coding tasks: `command` expectations run hidden tests, a linter or a build on a copy of the agent's final work and pass on an exit code or named tests; a `reference_solution` proves a task solvable, and `skill-eval check-tasks` checks it with no model call, including that the unchanged task fails its new tests.
- Several participants in one run: a `conversation` with a simulated user who knows only its card, or a `pipeline` of stages that each see only what they declare (such as two independent reviews and an adjudicator); arms may differ in their participants.
- Host extensions can be built from an exact commit or a committed folder, arms may differ in declared environment variables, and `run --source <arm>=<commit>` measures an arm at another commit without editing the definition.
- A subject may use a shell only behind a declared isolation that the evaluator first proves confined with six probes, or in a container from a digest-pinned image through the standard `docker` command; when something is missing, the run says exactly what and how to install it, and never installs or pulls anything itself.
- `skill-eval run` gains `--jobs` and `--cpu-jobs` for parallel subjects and local work, `--reuse` to count identical earlier runs instead of rerunning them, `--pilot <n>` to try the first groups before the batch, and `--results <dir>`; `skill-eval view --html <file>` writes one self-contained page of a result.
- Evaluate Behavior guidance covers each eval mode, how to size and read results (claim classes, run-to-run noise, held-out cases, fair tasks, judge practice), and how to measure reviewers and other detectors on clean, seeded and real cases. Write Skill adds choosing what to change from evidence, a deletion trigger, and one authoring loop; Review Work's judge contract covers rubric judges, and its eval-definition review checks a definition before any run.
- `skill-eval review --limit <name>=<chars>` sets how much the advisory reviewer is shown (each response, tool-call arguments, each file, and the task materials in total; the defaults are unchanged). The review records the effective limits, and anything cut is recorded as the contract gap `materials truncated`, because the judge contract asks for full files.
- Adds Task Memory on native Pi as a preview, off by default (the Task Memory switch in `/freeflow settings`, or `taskMemory.enabled`). A session attaches the Working Records it works on; Freeflow delivers the focused record's resume view when it becomes the focus and after a compaction, reload, resume, fork or `/tree` navigation, and refuses record writes to records the session has not attached. Projects group tasks, with records under `~/.freeflow` (or `FREEFLOW_HOME`), IDs such as `my-app/task-003` and one owning session each; each task's resume view lists the project's other tasks, which the agent reads and searches when they bear on its work. Fan-out creates a child record with its own Git worktree and branch for a parallel session and gives a command to paste into a new terminal, where Pi offers to attach the child. Everything can be asked for in plain language ("list my projects", "open the retry task", "split the parser off"): the agent proposes, and anything that creates something or lets the session write opens a dialog for the user to confirm. `/freeflow task` and `/freeflow project` commands do the same directly. Task-memory steps and delivered resume views show as one line in the transcript and expand to the full text.
- Track Work gains projects, child records, task IDs, worktree fan-out (with a start command for the host's agent) and record search as `working-record.mjs` commands on every host, and `view entry <ID>` to read closed History entries by ID.
- On Codex, Claude Code, Gemini CLI, Cursor, and GitHub Copilot, a `prompts` setting in `.freeflow/config.json` or `.freeflow/local.json` turns each of Freeflow's session-start prompts on or off: `core`, `interactionContract`, and `workingMethod`, each on by default. Pi always delivers all of them.
- A `review` setting in `.freeflow/config.json` or `.freeflow/local.json`, on every host, sets when finished work gets an independent review: `mode` is `auto` (the default: Review Work's risk check decides), `off` (the agent only proposes a review, with its reason and cost, and runs it on your yes) or `always`, and `model` names the model a reviewer runs on. The personal file overrides the shared one field by field, and `auto` there returns a shared choice to the default. A setting other than the default appears in the agent's Runtime State, so the agent follows it without reading the files.
- Task Memory works under automatic Cognitive Routing: the Coordinator handles task memory with you, Helper and Executor workers only read it and put any action they need in their report, and every profile receives the focused record's resume view, also after a worker compacts.
- Task Memory's `taskMemory.autoApprove` switches let the agent take some actions without the confirmation dialog: `attach`, `create`, `env`, `fanout` and `projects`, each off by default and set in `/freeflow settings` (Personal or Repository) or a config file. An action taken this way says so in the transcript.
- On Pi, the agent can put a choice that is yours to make into a dialog (`ask_user`) and continue on your answer in the same turn, instead of asking in its reply and stopping: one to four questions, each with two to four options and their trade-offs, the agent's recommendation first, a row for your own answer and a note per question. `Esc` closes it without answering, and the agent then does not act on that choice. Without a UI the agent asks in its reply as before. Task Memory's confirmations use the same dialog.
- With Tool Execution on, `monitor` watches a command's output and tells the agent each line it prints as it happens, so it can react to a log or watcher while it runs, including after it went idle. Lines within 200 ms arrive together; a monitor ends when its command exits, after its time limit (5 minutes by default, at most 30) or with `stop_background`, and one that sends more than 20 messages a minute is stopped.
- On Pi, Messaging (a preview, off by default: the Messaging switch in `/freeflow settings`, or `messaging.enabled`) lets the agents in your Pi sessions on this machine send each other plain-text messages: ask one session to tell, ask or answer another, and the reply comes back on its own. A message reaches the other agent after its current tool calls, or starts a turn when it is idle; a session that has had no prompt yet shows it and reads it with your first prompt. A message is information from another agent, never your instruction. Ask before delivering (`messaging.inbound`) can hold messages for you to accept: never (the default), from outside the repository's Task Memory project, every message, or refuse all. Sessions are addressed by session ID and shown by name, and each step is one line in the transcript.
- Task Memory links each repository in a project, and each child's worktree, to the project's store at `.freeflow/project`, so you can open and edit its records in your editor while the agent works. The link is kept out of Git through the clone's `.git/info/exclude`, and made again at session start when missing.
- Task Memory can remove tasks and projects: ask the agent ("remove the trial project") or run `/freeflow task remove <ID>` or `/freeflow project remove <name>`. A dialog always asks first, names what goes and which Git worktrees stay. Removed records move to `~/.freeflow/trash/`, and only you delete them for good, with `/freeflow trash empty`; the agent cannot. Track Work's CLI has `task remove` and `project remove` for other hosts, and task numbers are never reused.
- Review Work reviews two more kinds of thing: a report or record of work done (a final report, a results note, a Working Record), checked claim by claim against the outputs and files it describes; and an eval definition (a case, suite, fixture or grader), checked before its runs are paid for, for whether a correct answer can pass, a wrong one cannot, and its defects are real. It also adds a judge contract for any model whose verdict on another agent's output is used as evidence: what to record about the judge, what it must be shown, and how to combine verdicts. Before a model reviews anything, the deterministic checks that apply run first, and an adjudicated review is recorded in the task's Working Record.
- Evaluate Behavior can run a subject with Freeflow loaded, built from an exact commit, with repository and personal settings declared in the configuration and checked by that build's own validator before anything runs; comparing two settings, such as Task Memory off and on, is one `component`. `run` prints its plan (subjects, models, Freeflow builds) before starting, and asks on an interactive terminal unless `--yes` is given. Aggregates now count grade errors and run states, report pass^k per check (whether it passed in every trial) and the per-trial pairs per comparison, and name the strongest claim the counts support. A `file-text` expectation can check one `line`, such as a review's first-line judgment.
- `skill-eval review` checks its reviewer against Review Work's judge contract: it shows the reviewer the task's fixture and each run's written files in full, hides run paths and arm names, records the reviewer's model family against the subject's, and with `--swap` reviews again with the runs in the other order to show whether position decided the answers.
- Evaluate Behavior body groups may give the subject Pi's `ls`, `find` and `grep`, confined like `read`: without a path they work in the run's workspace, and a path outside the evaluation environment is refused. A reviewer can then list the files it was given instead of guessing their paths. `bash` and `powershell` stay unsupported.
- An eval configuration declares the host's Pi extensions and settings: `host.extensions` names installed Pi packages by exact name and version (such as an Anthropic subscription's auth extension), and `host.settings` becomes each subject's Pi `settings.json`. Both are recorded with every run and may be the compared component, so a definition can evaluate any Pi setup, not only Pi's defaults. `skill-eval review --configuration <file>` gives the advisory reviewer its model, extensions and settings the same way.
- Evaluate Behavior can run its agents in Claude Code as well as Pi: a configuration with `"host": { "name": "claude-code" }` runs subjects, judges and simulated users in headless Claude Code, with only the declared tools, no settings, instruction files, MCP servers or slash commands from the machine, and the same confinement as on Pi. Bash runs only in a container environment, and the login comes from your environment (such as `CLAUDE_CODE_OAUTH_TOKEN`, which `claude setup-token` prints), never from a copied file. Each run records what Claude Code sent to the model, since Claude Code adds a line about itself and a note about the environment to every request.
- Evaluate Behavior accepts an optional group field `"revision": "description-only"`: before any subject runs, the evaluator checks that the two target skills differ only in their frontmatter description, and refuses the group otherwise.
- A Working Record can hold a Work agreement: an optional `### Work agreement` heading directly after Goal, for what done looks like, what the agent does without asking, what needs your yes first, where it comes back and how long that holds (each line led by `Done when`, `Without asking:`, `Ask first:`, `Back` or `Holds until`), with your reply quoted. `init` writes it only when its input has one, and `validate` rejects it when empty or anywhere else. Records without it stay valid, and nothing is migrated. In a record that has one, return conditions and actions that need your yes move there from Boundaries.
- Verify Work checks changes to existing tests: `test-changes.mjs` lists every test file, fixture, snapshot and shared test setup file that changed, moved or was deleted since a base commit, with the changed hunks, and the agent gives each one a reason (it keeps what the test checked, or follows a behavior change you agreed) or brings it to you before calling the work done. Its guidance also asks new tests to assert only agreed behavior, names signs of a test too weak to catch a bug, runs a bug fix's regression test on the unfixed code, bounds a speedup by the share of the run that changed, and treats a no-regression claim without a baseline as unproven.
- Write Docs covers a feature map: one file per user-facing feature in the developer docs, saying what the user sees and the exact steps and results that show it working in the running software, plus one shared guide for launching, checking, driving and cleaning up, and which steps cost a model call. When a project with code has no developer docs, the agent recommends creating them and waits for your yes, instead of putting that knowledge in `AGENTS.md` or `CLAUDE.md`.
- Verify Work uses a project's feature map when a claim needs the running software: it finds the feature files that cover the changed code, reads only those, the shared guide and its helper, drives the steps through the saved helper, and when a step fails decides whether the steps drifted, miss the claim, or the product is wrong. A product bug is reported, never written into the steps. Corrected steps are saved with the change when your agreement covers docs, and proposed otherwise.
- Write Docs' docs check gains `--covering <path>`: it lists the documents whose `Covers` header includes each path (the file, or a folder holding it), with the commit each was verified at and whether it is current or stale, so a change can find the docs it should reread. Without document arguments it searches the project's docs index, and it reports how many documents have no `Covers` line.
- Write Docs has a default developer-docs layout for a project that has none (`dev-docs/` with an overview, then `subsystems/`, `features/`, `guides/` and `adr/` as each is needed), proposed to you rather than created; a project with its own docs keeps them, found in the order `dev-docs/README.md`, `ARCHITECTURE.md`, a `README.md` in `docs/`. It also says which kind of knowledge belongs where: developer docs, instruction files, the task's record, or your host's memory.
- New skill, Map Features: when you want a tested way to check your software live, the agent studies the repository and writes a feature map in your developer docs (one file per user-facing feature, with the exact steps and the results to expect), a shared guide, and a helper script that launches the software in an isolated run, drives it the way a user does, keeps evidence, and cleans up. It drives every step it writes before calling it verified, marks the rest unverified, and later rechecks the map feature by feature when you ask, reporting a product bug instead of editing the steps to pass. Steps that call a model or another paid service run only with your yes, and the helper starts the software without credentials otherwise. Verify Work proposes it when a claim needs the running software and no recipe exists.
- Evaluate Behavior pipelines can hand a stage's whole workspace to the next: `sees: ["<stage>.workspace"]` starts that stage in a copy of the earlier stage's final workspace, binary files included, so it can run what the earlier stage wrote. `<stage>.files` still delivers written files as text to read.
- Before any container starts, Evaluate Behavior checks that your container engine shares the folder the workspaces live under, and refuses with the folder and the fix when it does not. A VM-based engine such as Colima shares only your home folder by default, so a workspace elsewhere (`check-tasks` uses the system temp folder) used to arrive empty and fail its graders for no visible reason.
- Execute Work covers one mechanical edit repeated across many sites: the agent edits the first site by hand, writes a script or codemod, checks that the script reproduces the hand edit on that site, then runs it on the rest and points to the script in its report so a reviewer can rerun it. A few sites, or sites that each need their own decision, are still edited by hand.
- `skill-author compare` reports what a revision of skills, references, runtime prompts or AGENTS.md no longer says: with no arguments it compares the working tree, uncommitted edits included, with where the branch left the default branch, or two named refs, or a folder copy (`--base`) for text kept outside Git. It lists every bullet, step, table row and sentence that was dropped, moved or reworded, and exits nonzero while a dropped rule (under a Rules heading, a numbered step, or a never, always, must, only, do not or stop sentence) has no verdict in a `--verdicts` file. `skill-author validate` now lists link cycles among the references a skill reaches, and with `--routing-map <file>` checks that the map's row for the skill names the same sibling skills and resources its `SKILL.md` links.

### Changed

- Evaluate Behavior's authoring references no longer restate the field rules its loader enforces with an error naming the field; they point to `skill-eval check-tasks`, keep the rules needed while designing a group as one line each, and keep meanings, defaults and choices.
- Evaluate Behavior checks expectations and a suite's decision when the definition loads, so `skill-eval check-tasks`, `run` and `npm run check:eval-definitions` refuse them before anything is spent, where before most became grade errors after the subjects were paid for. A kind in a group type that cannot grade it (such as `response-text` in a description group or `skill-read` in a body group), a `variant` that is not an arm, a `turn` the input does not declare, a value its grader rejects, or comparison members that are not one check is refused; so is a decision that could only exclude cases: a group without a decision arm, a measure recorded in one decision arm but not the other, an unknown metric, or a measure no group records in both arms. A group that records the measure in neither arm, such as a control case, still loads. An unknown expectation kind still loads and becomes a grade error.
- Evaluate Behavior names the group's file when a suite's group fails to load (`group <id> (<file>): <reason>`), in each `check-tasks` line, and when a reference check refuses a run.
- Write Skill has new rules for shaping skills: a skill's main file must be enough for the common case, with a routing table first and a reference only for a narrow, large situation; a script or tool output is preferred to prose that may never be read; skills that do one job split by type are merged; a removed or merged skill gets no alias. Before committing a substantial revision, the agent runs `skill-author compare` and settles every rule it no longer states, which replaces snapshotting the old package by hand. Its five references are now two: Placement And Dependencies (where text lives, references, scripts and how skills depend on each other) and Activation And Wording (when a skill is read and how its text reads); update links to the old reference files.
- Cognitive Routing's skill is split by role: the skill keeps what every profile shares, and the Coordinator's method (with one section per delegation mode) and the workers' method are the references `coordinator.md` and `worker.md`, replacing `helper-mode.md`, `executor-mode.md` and `both-mode.md`. Under automatic routing each profile now reads the skill and its own reference before its first command or edit, and Freeflow refuses those calls until both are in view; a worker reads about 2,200 words instead of 3,700. Update links to the old mode references.
- Setup Freeflow is one skill file: its activation-contract and host-setup references are folded in, with the unsupported config keys in one list. Update links to `skills/setup-freeflow/references/`.
- Rules repeated across skills keep one owner: what counts as a choice that is yours is defined once in Discuss Work, which now also owns the self-review decision check; the others point there. Verify Work's two report shapes are one.
- Review Work, Verify Work and Evaluate Behavior state each rule once and keep fewer, larger references, one per situation. Review Work's review gate is now in the skill itself, and its references are `work.md` (now with the security risk lens and the work reviewer's brief and instructions), `artifact.md` (now with reports and Working Records, and the prompt for any independent review that is not of work), `adjudication.md`, and `evals-and-judges.md` (eval definition review and the judge contract); `reviewer-contract.md`, `review-gate.md`, `report-and-record.md`, `security-risk-lens.md`, `eval-definition.md` and `judge-contract.md` are gone. Verify Work's integration, browser, performance and project-recipe references are one `runtime-evidence.md`. Evaluate Behavior's core is shorter, opens with a routing table, and has five references: `design-and-measurement.md`, `authoring.md` (the definition schema), `coding-tasks.md`, `conversations-pipelines-judges.md` and `running-and-evidence.md`. Update links to the old reference files.
- An independent reviewer runs only what its brief's `May run` line names, by default the project's declared checks (tests, build, typecheck) in its own copy, and Verify Work now counts that line, like your request, as covering the checks it runs. A report or Working Record is reviewed as an artifact.
- An independent reviewer of work is now briefed with pointers to its inputs (the Working Record, the covering dev docs, the Review Rules, the diff range, the builder's evidence, what it may run, and where to write its report) instead of a long prompt with everything pasted in.
