# Changelog

## Unreleased

### Breaking Changes

- Track Work's `init` makes a Schema 5 task folder and needs `--cue` (when the task matters, starting "read when"); `init --schema 4` makes the Schema 4 record Pi's Task Memory keeps until Pi moves to Schema 5, and Task Memory's own commands already ask for it. A script that ran `init` without `--schema` gets an error naming both.
- Evaluate Behavior's `skill-eval run --dry-run` is now `--uncommitted`: it always ran subjects and called models, and only allowed uncommitted inputs, so the old name promised a run that spends nothing. `--dry-run` is refused with a message naming the new flag; stored results keep their `dryRun` field and still read.

### Added
- Track Work's `delegate open --scratch <folder>` keeps a delegation with no task: the same brief from the template under the folder's `delegations/`, with nothing recorded, and `delegate check-return --scratch` checks its return. Freeflow's core prompt now names Execute Work's delegation reference whenever work goes to another agent (a subagent, parallel workers, a reviewer or any multi-agent orchestration), with or without a task.
- Setup Freeflow sets up the Freeflow store that keeps task memory, in a reference of its own: it asks local only or local + cloud, local only by default, makes it with Track Work's `store init` (or `store init --remote <url>` for your private repository), says what to set in a cloud environment (`FREEFLOW_HOME` at the store's clone, a setup-script line that clones a Freeflow release, and the store attached to a session when its work needs task memory), and moves older records into the store: Schema 4 records and Pi's Task Memory with `migrate --project`, which converts a copy, and Schema 5 tasks kept in a repository's `.freeflow/tasks/` with the same command, which copies them unchanged; the originals stay. A task always lives in the store: where you want no store, there is no task.
- At session start, Freeflow on Claude Code says what keeps the session from a working store and whether you or the agent fixes it (`session status`'s new `missing` list): a store `FREEFLOW_HOME` names that is not there, an empty clone not laid out yet, a cloud session's store with no remote. Where no task names the session's folder, as in a cloud session that starts in the store, the menu lists every open task in the store; and `task here --scan <folders>` finds where a task's repositories are on this machine, so recovery reads their files in a fresh container.
- Track Work's tasks may belong to no project: `task create --no-project`, or with no project naming the repository, makes `task-NNN` in the store's `tasks/`, the session-start menu lists it under "No project", and `task move --id <ID> --project <name>` (or `--no-project`) moves a task's folder into a project or out of it, with the next number there and Git keeping its history. `estimate` gives the context's use against the window and the point where Freeflow's notice comes, from `--used` or the session's transcript, and with `--done` and `--left` projects whether the rest of the work fits in this cycle; where no window is set and the context is larger than the one it would assume, it asks for `--window`.
- Freeflow on Claude Code (2.1.287 or later) carries a Schema 5 task through compactions by itself, wherever a Freeflow store exists; elsewhere it does nothing. At session start, `/clear` and resume it pulls the store and gives the agent the menu of the project's tasks. As the context nears Claude's own compaction it tells the agent to checkpoint, and once the checkpoint is done it compacts the session at the turn's end with the task's bundle in place of the conversation, with no summary request, then starts the next turn so the work goes on. A compaction that comes before the checkpoint is Claude's own, with the bundle as of the last checkpoint and your messages since added after its summary. Reading and editing files inside the store no longer waits on a permission prompt or auto mode's check, as in a working directory where edits are allowed; a deny rule still holds. It also syncs the store when a turn changed it, reminds workers whose prompt names a delegation to keep their `progress.md`, sends back once a return that is not ready, and releases the task at session end. Track Work's script gains `session status` (this session's state in the store, as JSON for such a layer) and `view bundle --fallback`.
- Track Work's script sets up the Freeflow store, one Git repository that holds every task's memory. It is local by default (`store init` makes it on this device, and nothing leaves the machine), and a cloud store with your private repository: `store init --remote <url>` clones it into the Freeflow home and, when it is empty, lays the store out (`store.json`, ignore and merge rules, `rules/`, `projects/`) and pushes a first commit authored as you, or joins a store another machine made, and `store remote --url <url>` moves a local store's whole history into an empty repository; `store status` says what is not committed or pushed; `store sync` commits, takes the remote's commits and pushes, or with `--pull` only takes them. Sync keeps working without a network (it commits here and pushes next time), retries a push the remote refused because it moved, merges `history.md` and `sessions.md` by keeping both sides' lines, stops on any other file both machines changed with both copies kept until `store sync --resolved`, and scans every push for common secrets, naming a found one by path and line and never pushing a commit that held it. A home that holds Pi's Task Memory is left alone, and records inside the store pass Track Work's Git check.
- Track Work's script keeps Schema 5 tasks, beside Schema 4 records, which keep working as before. `init --schema 5` makes a task folder: `record.md` (Current Context, Current Work with the open agreement, the Slice, delegations, Space and what to read, and Future Work), `history.md` and `decisions.md`. `agreement open`, `update` and `close` keep what the user agreed, in their words; the slice commands and `task set-state` work on it; closing a Slice or an agreement appends its one History entry (with the Slice's updates, or the agreement's lines, updates and decision list) and commits and pushes the store; a close that stopped halfway finishes when run again. `checkpoint` checks the folder's structure and the recovery budget, writes where the work repository stands and pushes the store. `view recover` says the record is memory and your direction decides the work, then prints the rules, the record, the decisions within their budget, the History index, the project's other tasks and the checks; `view entry` and `view index` read History. In a Freeflow store, `project new`, `remove`, `list` and `show` and `task create`, `take`, `release`, `switch`, `here`, `search` and `remove` work on its folders (elsewhere they keep using Pi's Task Memory registry): a task's `sessions.md` says which session holds it, a second session's `task take` is refused until the holder releases it or you agree to a takeover, `task here` prints the session-start menu for the folder's repository, and a removed task stays in the store's Git history.
- Track Work's script carries what shaped the work across compactions, converts Schema 4 records, and measures recovery against a budget. `discussion list` numbers your messages since the last checkpoint, read from Claude Code's session log or a plain `User:`/`Assistant:` export (`--transcript`), messages sent while a turn ran included and resends left out; `discussion save` keeps the ones that shaped the work, word for word, as a block in `sources/discussion.md`, each with the agent's line saying what it answered; `discussion drop` removes a block, and `checkpoint` lists the blocks whose work is closed. `migrate` converts a Schema 4 record to Schema 5, in place or into the store with `--project`, keeping the old record whole in `sources/`. The recovery budget counts only the memory the agent shapes and scales with the square root of the context window (about 10,000 words at 200,000 tokens, from `FREEFLOW_CONTEXT_WINDOW`), in normal or expanded mode (`task set-budget`); Current Context and Future Work keep fixed budgets, and the rules, the skills and the record's new Defined by section (accepted Specs, Plans and the skills the work follows) are read whole and never counted. `budget` prints it before the agent writes, and `init` and `checkpoint` print it too; it only warns. `checkpoint --input` rewrites the record's new In flight section (where the step stands, what was observed, tried or is pending, and files to carry); `view bundle` prints everything recovery reads, each source whole, with its sizes; without a task, `checkpoint --session` writes a session summary that `view bundle --session` prints.
- Track Work's script keeps delegations for Schema 5 tasks: `delegate open` assigns `D-NNN`, writes the brief in `delegations/D-NNN-<slug>/` from the template, makes a writing worker's worktree on its own branch at the base, and writes the delegation's line in Current Work; `--parent` opens a sub-worker's delegation inside its worker's folder and refuses a fourth level. `delegate amend` appends a dated change to the brief; `delegate status` lists open delegations and their sub-workers; `delegate check-return` refuses a return with a missing heading or a commit that is not on the brief's branch; `delegate close` records the outcome, model, effort, tokens, minutes and merge commit in one History entry. `view recover --delegation <ID>` is a worker's recovery: its rule, then its brief, progress and return. Execute Work's delegation reference names these commands where a step used to be kept by hand.
- Evaluate Behavior's pilot (`--pilot`) checks each shell arm's harness before its first subject, with no model call: a command in the workspace, one naming a path outside it, the first command again, a write under `/tmp`, and which of `node`, `python3` and `git` the shell has. It stops the pilot when the shell stops working after a probe or the arms found different things, and otherwise prints the findings, which apply to every arm.
- Evaluate Behavior refuses a run before any subject when a container image an arm runs in, or the engine that runs it, is missing, saying what to install or pull; nothing is pulled.
- Research Work's `study.mjs lock` refuses a study plan whose pilot shows the reference arm passing every unit, since such a study has no room to show a gain, unless `--saturated` gives a written reason, which the lock records. The plan records the pilot in one `Pilot result:` line.
- Execute Work has a delegation reference for handing work to other agents (subagents, parallel workers, reviewers, trial and eval agents): when handing work out pays, the smallest capable model by default and the strongest only with your yes, briefs that point to files, one folder per delegation holding its brief, progress and return, writers in their own worktrees, a return checked before it is accepted, and each delegation's model, effort, tokens and minutes recorded. A worker may hand mechanical checks, gathering or research to sub-workers on the smallest model, three levels at most, and only the agent you talk to asks you anything. Write Skill's trials, Review Work's reviewers and Research Work's workers point to it.
- Research Work's figures list x labels that overlap and text past the canvas, and an `x.rotate` option turns long category labels.

- Track Work measures what work uses and plans from it. `slice start`, each `checkpoint` and `slice close` keep, in one line the agent never types, the context a Slice added, the compaction cycles it touched, its working and wall-clock time and, per model and effort, its billed tokens and their cost at API list price, read from the harness's transcript (Freeflow's Claude Code mod names it) or given with `--used`; `delegate close` measures a worker from its own log. Each Slice starts with a prediction from past Slices (the task's, else its project's or the store's), corrected by how far past predictions were off. `estimate --plan` lays the Slices left across compaction cycles, flags any too big for one, shows what could run in parallel and prices past delegations and a fan-out; `estimate --project` and `--store` add up what was measured. Discuss Work's agreement shows the work's size in compaction cycles and its cost (`choices.mjs agreement --plan`), with the plan under Technical. Prices come from a dated list-price table that `FREEFLOW_PRICES` can replace; the planner shows costs and never picks a model.
- Research Work, a new skill (`/research-work`) for answering a question from evidence gathered and checked first, starting with in-depth reports on code, papers or docs: a research brief agreed with you, a source ledger saying how each source was checked, a claims register with an evidence level per claim, and checks that every `path:line` citation exists at its pinned commit, every quote appears in its source and every number in the report traces to a registered claim. Its statistics script gives intervals, paired comparisons, clustered runs, rater agreement, multiple-comparison correction, pass@k and power, and Evaluate Behavior now uses it.
- Research Work runs studies and quick checks: a study plan answering twelve questions and locked before the runs that count, a receipt for every run (failed ones included), deviations logged with who cleared them, a validation record before a model judge's verdicts count, and checks that a confirmatory claim was planned, that held-out items ran only under the lock, that every registered number appears in its result file, and that each judge score quotes the output it judged. A Bayesian interval covers pass or fail results in few clusters. The general method of study design and measurement moves from Evaluate Behavior into Research Work, and Evaluate Behavior points to it.

- Research Work writes papers: an outline checked against the claims register (a proposition a result could contradict, contributions with their claim IDs, one sentence per planned paragraph, figures with their data files, the objections and where each is answered), the writing techniques with the evidence behind each, one review and revision by patch, and a rebuttal ledger for the venue's reviewers that records your choice and reason for each comment, refuses submission while a commitment has no place it was fulfilled, and lists requests that are new in a later round. A literature review gets an evidence table. The research report's shape moves from Write Docs into Research Work, which states each finding's strength as its evidence level; Write Docs routes research documents there.

- Research Work has tools for writing the paper: figures drawn from their data files with a receipt the outline checks, a bibliography from the source ledger that marks every source not verified, checks a draft must pass before review (abstract numbers in the body, citations, figure and section references, word limits), a venue copy without claim IDs, revision by patch where each change names its finding, a build to PDF, Word, LaTeX or HTML through Pandoc, a check of the built PDF's pages, words and required sections, and a default project layout.

- Research Work checks three things its guidance asked for: a claim that something is new cites the search behind it, every analysis variant a study plan lists is reported, and a plan can declare the models in its method with their exact snapshots (`study.mjs check` notes a plan that does not). A literature review's evidence table can name each study's weakness.
- Research Work aggregates results over several seeds and tasks: the interquartile mean, mean, median and optimality gap with stratified bootstrap intervals, the probability that one method beats another, and an interval for pass^k for one task or a suite.
- Research Work checks more of a study before its result counts: the plan names the method that computes each confirmatory rule, and a verdict computed by another method is refused; a model that labels the data counts as a judge; the arms compared get the same budget; a validity check that fails holds the analysis until you clear it; the plan records how each route of contamination is controlled; and the plan lists each source of variance. Weighted kappa takes quadratic weights and reports raw agreement beside it. A study with human participants stops for you and your institution.
- Research Work checks that a key claim's cited lines or passage actually show it: a separate reader sees only the claim and its evidence and answers supported, partial or unsupported with a quote, and the check counts the answers and holds the report until each partial or unsupported one is settled. Lookups no longer verify a correction notice, a reply or another part of the work, or a record whose year or first author differs; a row with no identifier can be searched by title for a candidate DOI, and a dead link is looked up in the Wayback Machine. Reports and drafts get more checks: a percentage that does not follow from its counts, wording stronger than a claim's evidence level or against a number's sign, an undated "latest", passages copied from a source without quotation marks, and sources never cited. Rechecks add Cohen's d from t and degrees of freedom against the sample size, and accept a corrected p. Text inside a source is treated as data, never as instructions. A quote beside a source in any other form is listed as not checked rather than passed, and a citation sentence counts for the claim named right after it. Model names such as GPT-4 no longer count as numbers to trace, search counts trace to the search ledger, the bibliography takes titles and authors from verified lookups, and a source ledger's Supports is checked against the claims that cite it.
- Research Work rechecks the numbers another study reports: whether a mean, a percentage or an SD is possible for its sample size (GRIM, GRIMMER, DEBIT), and whether a p value follows from its test statistic, in a table whose verdicts only the computation can write.
- Research Work looks sources up online when you ask: a DOI through Crossref with any retraction or correction notice, an arXiv ID, whether a link's page names the source, each matched on the title and an author, cached so a second run stays offline, and never marking a source fabricated because nothing was found. A code citation can be checked against the lines the agent actually read. A study plan's lock names the git commit that holds it when the plan is committed, and a plan is refused when it stops as soon as a result turns significant or gives a comparison no sample size.
- Research Work supports systematic reviews: screening criteria tagged by stage, so a criterion that needs the full text cannot exclude a study at the title and abstract; a model that screens counts only with a judge validation record that passes; two screeners' raw agreement, kappa and the disagreements a person settles; a PRISMA-style flow figure drawn from the search ledger's counts, never typed; each study's risk-of-bias tool and judgment in the evidence table; and `stats.mjs meta`, fixed and random-effects pooling with tau², I² and the Hartung-Knapp interval, matching statsmodels on the BCG vaccine trials. The paper guidance says what an abstract holds.
- Research Work's systematic-review checks hold tighter: a model screener's judge record must be for the rubric the model was given; a flow figure is recomputed from the search ledger it names, so a count edited by hand is refused even when its sums still add up; a hit both screeners decided cannot be left in another state without a person settling it; `stats.mjs meta` warns when the Hartung-Knapp interval is narrower than the studies' own evidence and gives the truncated interval to report instead; a randomized trial with a secondary cohort analysis is no longer refused RoB 2; and `stats.mjs meta --method leave-one-out` refits without each study in turn and names a study the pooled answer rests on.
- Research Work fits a review the agent runs: the reviewing agent can record itself as the screener, without a judge record, and the counts and flow say it screened alone; citation chasing is its own method, counted apart from the databases as PRISMA does; a query can carry the service's own count of records returned, so those not screened show in the flow; a claim above L1 citing a source whose recheck is a mismatch is refused when the recheck table is given; `stats.mjs effect` makes risk differences, log odds ratios and log risk ratios with their variances, unpaired or paired, in the form `meta` reads; and `init project --kind review` lays out a review's synthesis folder without the study and paper folders. `validate` now notes and ignores `--sources` on an artifact that does not read it.
- Research Work checks a report or paper with one command: `research.mjs gate <folder>` takes the rigor from the brief, runs every offline check that rigor requires on the files present (the brief, ledgers and register, the study's records, citations and numbers, a paper's draft checks and PDF, and at publication rigor every source opened and the citation-support answers), and prints each check as passed, failed or not run with why, then what is left before the work goes out. Evaluate Behavior says how a Research Work study plan's method, budgets, validity check, contamination and judges map onto its runs; Review Work's Judge Contract covers the citation-support reader; and the open choices of a research brief and a study plan go into the task's decision list.
- Research Work's gate says what it did not check: at publication rigor it names every claim the report or paper cites that has no support answer, for you to add or keep out with `--unsupported-ok`, which it lists as not checked; a paper's PDF counts as checked at publication only against the venue's limits or required sections it is given, and with none given it is not checked (below publication a PDF is shown without holding the gate); a passed check's notes print beneath it; a report that cites nothing is not checked; and a register with a confirmatory claim but no study plan fails. The packets for the support check can come from the report and the paper together. The gate finds a source's saved copy in the sources folder by its ID or pin, so quotes are checked without a `--copy` for each.

### Changed

- Discuss Work's agreement reply puts its Size line last, after Technical, so the work's size stands out.
- Track Work's guidance describes Schema 5 tasks: taking only the task your message points to from the session-start menu, the agreement in your words, Slices with one-line updates that point to their evidence, the recovery budget, the checkpoint at a safe point before a compaction or a transfer, and recovery from Freeflow's bundle. Freeflow's core prompt, Execute Work, Deliver Work, Discuss Work, Research Work, Write Docs, Review Work and Write Skill say so. Deliver Work's rule against publishing Working Records names the Freeflow store's task folders too, and lets only Track Work's script sync the store, to your own private remote. Discuss Work's `choices.mjs --record` reads a Schema 5 task's `decisions.md`, and its catch-up the current Slice's update lines. Review Work's briefs say that reading files is inspection, not a check that needs `May run`.
- On Claude Code, Freeflow's checkpoint notice comes once a compaction cycle and no longer repeats every 5%: it asks the agent to keep working to a safe point (a finished step whose result it knows), then checkpoint and end its turn, and says where Claude Code would compact on its own. Before it, a one-line row shows the context's share at 50%, 60% and 70% of the window. The rows and the notice name the compaction cycle, counted for each session in the store and kept when it is resumed. A worker gets one notice in each of its compaction cycles.
- Evaluate Behavior runs four subjects at once by default, or one per two CPUs when arms run in containers; `--jobs 1` runs one at a time. Its skill gives every eval one route: count the runs, `check-tasks` for a coding task, a pilot, `--max-cost` from the pilot's cost per run and your yes, the batch in the background, `--reuse` after a stop, and flagged runs held out until you clear them.
- Write Docs' docs check can move a stale document's `Verified at` itself (`docs-check.mjs <docs> --stamp`), so the document goes into the same commit as the code it covers instead of a commit of its own. Feature files, which only driving updates, are left alone.

- Write Skill tries a new or changed skill on a real task before measuring it: Evaluate Behavior's new Trial mode runs one agent that keeps a friction log, which Review Work adjudicates like a review. Evaluate Behavior now asks for your yes, with the run count and estimated cost, before any run that calls a model, unless the task's agreement already covers it, and never asks a measured arm for notes.
- Research Work's citation-support check judges the claim as the report states it: each packet carries the report's and paper's sentences that cite the claim, so a sentence that drops a condition is caught, and at publication every cited claim needs a packet, quoted or not. A paper's quote form `"the exact words" [@S3]` is checked like `(S3)`, a verdict may quote one whole short line, and a quote's passage keeps its line breaks.
- Research Work's gate checks what it used to skip: a review's numbers against the result files its register cites, even with no study plan; a review's evidence table against the source ledger; and a report or paper given on stdin (`--report -`). A study or publication plan must have its method, budgets, contamination record and models before it is locked, and a lookup no longer verifies a "Part I" record for a "Part II" source.
- Research Work's guidance is in three references, one per stage (`evidence`, `study`, `reporting`), instead of seven, so a stage's guidance and its formats are in one file and a route opens one or two files instead of three or four; each artifact's format now sits beside the method that writes it.

- Write Skill explains why one capability skill that routes to its references and scripts (a trunk) beats many narrow skills, keeps a trunk's body to its routing table, common route and Rules, and asks for a design record per skill in the developer docs; Write Docs adds the skill design record shape under `dev-docs/skills/`.
- Write Docs keeps history in git: developer docs drop their Changes lists, and decisions cite the commit where they were made.
- Model judges follow one rule across Review Work, Evaluate Behavior and Research Work: Research Work says what a judge needs before its answers count, a judge counts as calibrated only with a passing judge validation record (repeatability included; an advisory review needs none), and by default the judge is a different model from the one it grades, another family being optional. Literature reviews and other research that needs checked sources now route to Research Work, which still writes its report in Write Docs' Research shape.
- Review Work's independent reviewers may run probes of the changed code on scratch copies by default, and a code Issue shows the command run and what it printed; the adjudicator reruns a Blocking code Issue's command before accepting it. `review-packet.mjs` finds the project's Review Rules when they are a `## Review Rules` section of a Markdown file (`check-brief.mjs` refuses `Review rules: none` when one exists), points the reviewer at the base's copy of Review Work, reads a `REVIEW.md` from the base so a change cannot supply its own rules, takes Review 2's diff from the previous review of the same change when reviews of several changes interleave, keeps another change's brief that has not reported, and prints the correction diff's size for Review 2. Corrections that change what a check accepts or refuses justify a focused Review 2, and a new `check-adjudication.mjs` refuses a report until each item has an Accepted, Rejected or Open disposition with a reason (and refuses two items with one ID), and counts them for the Working Record's Review line.

### Fixed

- Freeflow on Claude Code no longer sends its "continue" prompt late. After its own compaction it prompts the agent to go on only when nothing else started the next turn: a notification or message queued during the compaction starts a turn that goes on from the record itself, and the prompt used to wait behind that turn and arrive after it, sometimes long after.
- Freeflow on Claude Code no longer loses a compaction the agent asked for with `checkpoint --compact` when queued input, such as a notification or a message typed during the turn, starts the next turn first: the request stays until the record replaces the conversation, the next turn end tries again, and a line in the conversation says when a compaction did not run.
- Track Work measures a Claude Code session that was resumed in another folder from its newest log, instead of whichever copy it found first.
- Track Work's recovery and Freeflow's compaction bundle find the files a task names in the repositories it changes, such as a skill or `AGENTS.md`, when the session runs outside those repositories: a pointer that is in neither the task folder nor the work repository is looked up in each repository the record's Space names, where the store last saw it on this machine. An entry under Defined by or Read on recovery that names no file now gets a line in the checks, instead of being left out without a word.
- Freeflow on Claude Code gives a session your rules at its start, after the task menu: the store's `rules/` and those of the folder's project and of the task the session holds. Before, a session saw them only once it took a task and recovered it. Track Work's `task here --rules` prints them for any harness layer.
- Freeflow on Claude Code takes up a store added to a session that has already started, as a repository attached to a running cloud session is, at the end of that turn: the transcript that measures Slices, a pull, the scan for a task's repositories, and the store's file permissions, which it used to leave off for the rest of the session.
- Track Work's `validate` no longer takes a session's ID, a hex word after "session" in a Slice's update line, for a commit that does not resolve.
- Track Work's `store init --remote <url>` uses a folder that already holds an empty clone of that repository, as a cloud session has it, instead of refusing it.
- Discuss Work's `choices.mjs validate` accepts a decision list with no items yet, such as a new task's `decisions.md`, and its catch-up no longer lists a Slice's `Predicted:` and `Measured:` lines as work that ran.
- Track Work's `checkpoint --input` takes a labelled In flight line that says only `none` (`- Carry: none`) as no line, instead of refusing it; a plain line under Future Work is refused with the shape a proposed Slice takes; and a Schema 5 Slice accepts the `Review gate` line Review Work records.
- Claude Code no longer reports a failing hook ("Cannot find module '/hooks/adapters/gemini-session-start.mjs'") at every session start: it reads Gemini's `hooks/hooks.json` from the plugin's root beside its own hooks, and that hook now names its adapter so it resolves under both hosts and stays silent under Claude Code.
- Research Work's judge validation record accepts `not applicable` for Both orders when the judge rates one output at a time, so a rubric judge's record can pass; Review Work and Evaluate Behavior now say that `review --calibrate` gives agreement and kappa (the interval comes from `stats.mjs`), that a labelled judge is calibrated only with a passing record, and that an uncalibrated reviewer's verdict is weighed in adjudication, never obeyed alone.
- Evaluate Behavior's evaluator: a suite's decision cut short by the budget or a stop no longer claims "beats" or "worse" (its claim is `none`, reason `cancelled`, with the counts that ran and `k` the trials that completed); `--jobs` and `--cpu-jobs` hold even when a new start arrives as a slot is freed; the plan line also counts host-extension builds, which run on the host outside the seal; the transcript scan flags a host name with no dot, such as `http://intranet`, as an external network target (loopback and `localhost` stay internal), so more runs are held for you to read; judge calibration and agreement between two judges add linear-weighted kappa for `0-2` dimensions beside the unchanged kappa; and a decision or combined judge answer over a very long list of values no longer fails.
- `skill-author compare --all-units` lists every reworded unit that is not rule-like, under "Other reworded: confirm the meaning survived" in its JSON (`otherReworded`) and `--markdown` output, so the meaning check Write Skill asks for after a substantial revision can reach each one; the exit status is unchanged.
- Review Work's `review-packet.mjs`, run with `--root` from another folder, names the Docs and Review rules files relative to the repository instead of the current folder, so the brief it writes passes `check-brief.mjs` instead of being refused for paths that do not exist.

## 0.9.0 - 2026-10-24

### Breaking Changes

- Freeflow has ten skills instead of twenty-five, and the Workflow skill is gone: its body reached the agent only when the agent opened it, which it rarely did. Its cycle (agree before building, build and verify, review and hand over), what authorizes work, and where to stop are now in the always-present core guidance as "How Freeflow Works", and each skill's description says when to use it, so no skill routes the others; the line telling the agent to open a skill by its subject rather than a keyword is gone. Workflow's other parts moved to the skill open when they matter: route preparation, re-entry when the basis changes, and Domain Skill Composition to Execute Work; work that grows, remedies that change what you own, and its Asking The User reference to Discuss Work; questions and "stop" mid-work to the Interaction Contract. Every skill that said "return to Workflow" names the skill that takes over. No removed or merged skill or command below has an alias: update links, scripts and commands that name them, including `skills/workflow` and `skills/workflow/references/asking-the-user.md`. [How Freeflow Works](plugin-docs/workflow.md#what-changed-in-090) maps each removed name to where its job went.
- Discuss, Agree Work and Decision Gate are one skill, Discuss Work (`skills/discuss-work`, `/discuss-work`); `skills/discuss`, `skills/agree-work`, `skills/decision-gate` and the `/discuss` command are removed. The agreement now runs before building, and the core guidance carries it: the agent reads Discuss Work at a task's first request, before its first tool call, and before the first change on a task that builds or changes behavior it sends one message with what it will do, where it stops, and your decisions, each with its default and why, then waits. It lists every choice the request, code and docs leave open, technical ones too such as names, messages and files. "Go" accepts every default, and a correction changes only the line it names. A question needs no agreement; an exactly specified change, or a run where no one can answer, counts as one, with its defaults recorded and reported; a request that merely looks clear no longer stands in for one. The choices are kept in one decision list through the task (`sources/decisions.md` beside a Working Record, where only the choices you answered become Decisions), self-review checks the work against it, and the final report shows only choices you have not seen. Discuss Work's first page covers the common path: exploring while what or how is open, the agreement, when the wait is skipped, choices during the work, asking one question, and accounting at the end. A learning action (an experiment or prototype that answers one question, shared with Execute Work) and keeping a discussion across context loss are references read only when needed.
- The Action Selection skill is removed. Its description matched almost every search or command and its body was almost never opened; its one rule that reached the work, keeping tool output small and saying when it was cut, is now in the Working Method on every host, and the rest repeated the Working Method or other skills. The `/action-selection` command is gone. No alias replaces it.
- Bypass is no longer a skill, and `/bypass` is removed with no alias. Discuss Work now says what it did: when you explicitly ask to skip an optional step, such as waiting for the agreement, a plan, a review or a record, the agent skips only that, takes its defaults and reports them, still asks before a hard-to-reverse choice, and changes no authority, checkpoint you selected, or claim. When that skip must outlast the conversation and a Working Record exists, the agent records it in the Work agreement.
- Commit Work, Finish Branch, Release Work and Launch Work are one skill, Deliver Work (`/deliver-work`); `/commit-work`, `/finish-branch`, `/release-work` and `/launch-work` are removed. Its first page routes by situation and carries a plain commit in full: inspect, stage only what is yours, write the message, check the result. Closing a branch (a push, a merge or pull request, keeping or discarding it), a release and a production launch each have their own page, read only when that route applies. The rules the four shared, such as each route needing its own yes, never staging Working Records or secrets, and inspecting what changed before retrying a failed step, are stated once, with one stop list and one report. The commit step says to fix conflict markers or whitespace damage in the content they belong to, never to edit content just to silence the check.
- Design for Depth, Simplify Code, Diagnose Failure and Migration Work are part of Execute Work (`/execute-work`); `/simplify-code`, `/migration-work` and `/diagnose-failure` are removed, and so are Execute Work's Execute Work Edges and Domain Skill Composition references and Design for Depth's Implementation Decisions reference: what they held that nothing else did is now in Execute Work, its design reference and Track Work. Execute Work's first page is enough for ordinary implementation: a table of situations, the rules not already in the always-present guidance, what to settle before the first edit, one method at a time, where to go back when the evidence changes, and when to stop. Five references hold the rest, each read only when its situation arises: design (settling a choice later work depends on, interfaces, module dependencies, a change that keeps touching many places, and state that must survive failures), a behavior-preserving cleanup, a failure with no known cause, moving users or data to a replacement, and code practices, now read only before adding edge-case handling or a comment that explains why, which points durable rationale to the developer docs. Track Work's Checkpoint table names the skill that handles each Checkpoint when it is due.
- The Handoff skill and its `/handoff` command are removed; writing a handoff is part of Track Work (`skills/track-work/references/handoff.md`), opened when work pauses or passes to another session or person. Its page covers where the handoff goes (asking when that would change privacy, durability or audience), what the next context needs, and the templates. Resuming from a handoff goes through Track Work's own recovery, which now also says to check a completion, review or commit claim against its evidence before repeating it, and what to do with a handoff and no record. The Working Record format's second Checkpoint table is gone: the format points to Track Work's table and still reads the earlier type names. Update links, scripts and commands that name `skills/handoff`.
- Write Spec and Write Plan are part of Write Docs (`/write-docs`), now for any document a reader acts on; `/write-spec` and `/write-plan` are removed. Its first page says how specs and plans (task artifacts kept beside the Working Record, drafted and then accepted) differ from documentation (repository files that change with the code), states the shared rules once (a document grants no permission, no invented requirements, proposals labelled as proposals, claims checked against their sources), the shared method (reader, sources, shape, self-review), and the header, status and source trail for specs, plans and decision records, with one status list for all of them: `Draft`, `Reviewed`, `Accepted`, `Rejected`, `Superseded`, `Retired` (it replaces `Approved`, `Ready`, `Proposed` and `Abandoned`). A decision record can be `Retired`, with the date and the reason, when nothing replaces it, and a durable decision that shapes how existing software works is also stated, with a pointer to its record, in the owning subsystem doc's Decisions section. Two references hold the rest: spec and plan shapes, with decision records as one of its sections, and documentation shapes, which holds the reader test for a new or rewritten subsystem doc or overview. Update links, scripts and commands that name `skills/write-spec` or `skills/write-plan`, or their `spec-shapes`, `plan-shapes` and `artifact-standards` references.
- Review Artifact is merged into Review Work, and `/review-artifact` is removed: use `/review-work`, which now reviews code and other finished work as well as documents that guide later work (specs, plans, designs, decision records, handoffs and skills). Its rules, review budget and judgments are unchanged; each kind keeps its own sources, job checks and lenses, and one reviewer contract and one adjudication reference cover both.
- Evaluate Skill is renamed Evaluate Behavior (`/evaluate-skill` becomes `/evaluate-behavior`), and its subject is now any declared part of the agent's setup, such as its skills, instruction files, model, or host extensions and settings. Update links, commands and scripts that name `skills/evaluate-skill`; the evaluator script is still `scripts/skill-eval.mjs`, and definitions stay under `.skill-eval/`.
- Evaluate Behavior definitions are schema 2, and schema 1 files no longer load: rewrite them in the new shape. A group is now a task (prompt, fixture, tools, expectations) plus a `configuration` (host, model, the skill under test, and optionally Freeflow and a runtime); `arms.baseline` and `arms.candidate` each overlay it, and `component` names the only paths where the two may differ, such as `subject.source` or `model.thinking`. A group whose arms differ anywhere else, or that declares a difference that is not there, is refused before anything runs, and `component: []` runs the same configuration twice to measure run-to-run variation. `extends` shares one configuration file across groups. The authoring reference shows the full shape.
- `skill-eval run` refuses, before anything starts, a run whose inputs are not committed: the definition files, the fixture, runtime bundles, and working-tree skills and context must match the repository's commit, which the result then records. Add `--dry-run` to run anyway; the result is marked as a dry run and supports no claim. A configuration's `host.version`, when declared, must match the installed `pi --version`.

### Added

- On Pi, Freeflow pushes a few lines of guidance at the tool call that needs them: Deliver Work's commit essentials on a `git commit` result (with a reminder of Write Skill's loss check when the commit holds instruction text), the key lines of Execute Work's diagnose method when the same test command fails a second time, a reminder to run Execute Work's self-review when a test passes after a change, and, on the first tool result of a run while Execute Work is not in the agent's context, a request to read it (a read of a Freeflow skill does not trigger it, so reading Discuss Work first is not interrupted). The Guidance notices row under Tool Execution in `/freeflow settings` turns them off for the session, for you or for the repository (`toolExecution.guidanceNotices`).
- Skills now come with scripts that put the facts a decision needs in front of the agent. Execute Work's `touch-map.mjs` answers what a change touches (entry points, readers, writers, scheduled code, covering tests and the developer docs covering each file, each block saying what it did not search), and `self-review.mjs` writes one report before the agent reports a change: status, diff stat, every changed existing test or fixture with its hunk, each new test and whether it fails on the base, and whether each requirement's check ran after the last edit.
- Discuss Work's `choices.mjs` checks the decision list and renders the agreement, the hand-over's unseen choices, and a catch-up after an unattended run (defaults taken, choices waiting, what ran).
- Deliver Work's `delivery-state.mjs` reports branch, upstream, uncommitted work, an operation in progress, worktrees (flagging the session's own), the latest tag, version and changelog in one read-only call; `commit-state.mjs` tells your changes from pre-existing staged work; `release-preflight.mjs` and `push-route.mjs` check a release and a simple push locally without performing them.
- Review Work's `review-packet.mjs` prefills a reviewer's brief, names the review gate's triggers and the round budget, and runs `check-brief.mjs`. Write Docs' `plan-lint.mjs` lists Plan steps that name no check, and `artifact-check.mjs` checks a Spec, Plan or decision record's status and source trail.
- Track Work's `working-record.mjs view recover` gives, in one call after context loss, the resume view, each defining artifact and Recovery source with its trigger and whether it resolves, and where live Git state disagrees with the record; `validate` now warns about Material updates pointers (files, commits) that do not resolve, and `--strict` fails on those an Evidence or Result line names.
- Evaluate Behavior can declare Freeflow's Tool Execution tools in a container subject on Pi: `bash_background` and `monitor` run their command in the subject's container (they need a container environment in every arm), the folder where Freeflow saves their output is readable there, `stop_background` stops the command in the container as well as on the host, and `apply_patch` may only name paths inside the workspace. Freeflow's own checks of a shell command see it as the model wrote it.
- Evaluate Behavior body groups on Pi can close and resume the subject's session between turns: `input.resume_before` names the turns to resume before, with `runtime.session` on.
- `skill-eval check-tasks` lists, for every group, what the task's copy lacks against the setting it came from: Git history (a workspace is never a repository), ignored files the fixture holds (a clone lacks them) or the task names (such as `.env`), and tools or network the task asks for but the subject lacks, with each arm's tools and network. It reports these without refusing, and still calls no model.
- Evaluate Behavior scans every run's transcript and flags reads outside the workspace and declared resources, attempts to reach an external network target, reads of instruction files (`CLAUDE.md`, `AGENTS.md`, `.claude/`) outside the workspace, and hidden-test or reference-solution text in the subject's answer or files. A flagged run stays in the results but is held out of every count and decision, and stops a pilot, until you clear it with `skill-eval clear <result> --variant <arm> --flag <id> --reason <text>`, which records your reason beside the run and recounts every aggregate that lists it.
- Evaluate Behavior configurations can declare `network`: `"none"` seals the subject, so its bash, declared commands and command graders all run confined with no network and none of your files, including the provider login on disk, and a group that would run declared commands or graders on the host is refused; `"host"` allows them on the host on purpose. Each run records `sealing` (what its code could reach and where each part ran), the plan line names arms whose code would run on the host, and a declared command no longer receives the path of Pi's login directory or a login variable.
- Evaluate Behavior checks that each run shows a model at work before grading it: a run the host reported complete but with no assistant message, zero tokens, or no answer and nothing written (as after a failed login) is reported `invalid` with its reasons, never as a fail; it counts in no comparison, metric summary or decision, and it stops a pilot. Tokens are the signal rather than cost, which is zero for real work on a model with no configured price.
- Evaluate Behavior groups can run any number of named arms against a reference arm (`reference`, default `baseline`), or a single arm that measures one setup with nothing to compare (pass^k, metrics and judged scores, no comparison claim). Two-arm groups keep working unchanged.
- A suite can declare a `decision` rule before it runs (the measure, the two arms, the direction, alpha and the minimum cases): the aggregate then reports "beats", "worse" or "no difference shown" from an exact sign test over cases, and only then says "beats". A rule's `trials` schedule adds trials only to cases still undecided, up to a maximum.
- Every run records metrics (duration, turns, tool calls and errors, tokens, cost, cache hit rate), and an aggregate summarizes them per arm with paired differences against the reference; a decision can use them as its measure.
- Evaluate Behavior run metrics on Pi add `peakContext`, the largest single request a run sent (input plus cache reads plus cache writes), and `skillReads` and `skillReadTokens`, every read of a declared skill's files or of the loaded Freeflow package's skills and prompts, re-reads included, with tokens estimated from bytes. Aggregates report them per arm with paired differences, and a decision can use them as its measure.
- Judged evaluation: a group's `rubric` is answered by declared `judges` for each run alone, blind to its arm (`skill-eval review --rubric`), combined by a declared rule, stored apart from run and grade files, with agreement between judges and calibration against hand labels (`--calibrate`). `--swap-sample` checks order on a sample of groups.
- Coding tasks: `command` expectations run hidden tests, a linter or a build on a copy of the agent's final work and pass on an exit code or named tests; a `reference_solution` proves a task solvable, and `skill-eval check-tasks` checks it with no model call, including that the unchanged task fails its new tests.
- Several participants in one run: a `conversation` with a simulated user who knows only its card, or a `pipeline` of stages that each see only what they declare (such as two independent reviews and an adjudicator); arms may differ in their participants.
- Host extensions can be built from an exact commit or a committed folder, arms may differ in declared environment variables, and `run --source <arm>=<commit>` measures an arm at another commit without editing the definition.
- A subject may use a shell only behind a declared isolation that the evaluator first proves confined with six probes, or in a container from a digest-pinned image through the standard `docker` command; when something is missing, the run says exactly what and how to install it, and never installs or pulls anything itself.
- `skill-eval run` gains `--jobs` and `--cpu-jobs` for parallel subjects and local work, `--reuse` to count identical earlier runs instead of rerunning them, `--pilot <n>` to try the first groups before the batch, and `--results <dir>`; `skill-eval view --html <file>` writes one self-contained page of a result.
- Evaluate Behavior guidance covers each eval mode, how to size and read results (claim classes, run-to-run noise, held-out cases, fair tasks, judge practice), and how to measure reviewers and other detectors on clean, seeded and real cases. Write Skill adds choosing what to change from evidence, a deletion trigger, and one authoring loop; Review Work's judge contract covers rubric judges, and its eval-definition review checks a definition before any run.
- `skill-eval review --limit <name>=<chars>` sets how much the advisory reviewer is shown (each response, tool-call arguments, each file, and the task materials in total; the defaults are unchanged). The review records the effective limits, and anything cut is recorded as the contract gap `materials truncated`, because the judge contract asks for full files.
- Adds Task Memory on native Pi as a preview, off by default (the Task Memory switch in `/freeflow settings`, or `taskMemory.enabled`). A session attaches the Working Records it works on; Freeflow delivers the focused record's resume view when it becomes the focus and after a compaction, reload, resume, fork or `/tree` navigation, and refuses record writes to records the session has not attached. Projects group tasks, with records under `~/.freeflow` (or `FREEFLOW_HOME`), IDs such as `my-app/task-003` and one owning session each; each task's resume view lists the project's other tasks, which the agent reads and searches when they bear on its work. Fan-out creates a child record with its own Git worktree and branch for a parallel session and gives a command to paste into a new terminal, where Pi offers to attach the child. Everything can be asked for in plain language ("list my projects", "open the retry task", "split the parser off"): the agent proposes, and anything that creates something or lets the session write opens a dialog for the user to confirm. `/freeflow task` and `/freeflow project` commands do the same directly. Task-memory steps and delivered resume views show as one line in the transcript and expand to the full text. The `task_memory` tool's description names Track Work and the Task Memory skill, so the tool leads to them.
- Track Work gains projects, child records, task IDs, worktree fan-out (with a start command for the host's agent) and record search as `working-record.mjs` commands on every host, and `view entry <ID>` to read closed History entries by ID.
- On Codex, Claude Code, Gemini CLI, Cursor, and GitHub Copilot, a `prompts` setting in `.freeflow/config.json` or `.freeflow/local.json` turns each of Freeflow's session-start prompts on or off: `core`, `interactionContract`, and `workingMethod`, each on by default. Pi always delivers all of them.
- A `review` setting in `.freeflow/config.json` or `.freeflow/local.json`, on every host, sets when finished work gets an independent review: `mode` is `auto` (the default: Review Work's risk check decides), `off` (the agent only proposes a review, with its reason and cost, and runs it on your yes) or `always`, and `model` names the model a reviewer runs on. The personal file overrides the shared one field by field, and `auto` there returns a shared choice to the default. A setting other than the default appears in the agent's Runtime State, so the agent follows it without reading the files. On Pi, `/freeflow settings` sets both in the Personal and Repository scopes: the Review row cycles the mode, and Reviewer model picks from your authenticated models.
- Task Memory works under automatic Cognitive Routing: the Coordinator handles task memory with you, Helper and Executor workers only read it and put any action they need in their report, and every profile receives the focused record's resume view, also after a worker compacts.
- Task Memory's `taskMemory.autoApprove` switches let the agent take some actions without the confirmation dialog: `attach`, `create`, `env`, `fanout` and `projects`, each off by default and set in `/freeflow settings` (Personal or Repository) or a config file. An action taken this way says so in the transcript.
- On Pi, the agent can put a choice that is yours to make into a dialog (`ask_user`) and continue on your answer in the same turn, instead of asking in its reply and stopping: one to four questions, each with two to four options and their trade-offs, the agent's recommendation first, a row for your own answer and a note per question. `Esc` closes it without answering, and the agent then does not act on that choice. Without a UI the agent asks in its reply as before. Task Memory's confirmations use the same dialog.
- With Tool Execution on, `monitor` watches a command's output and tells the agent each line it prints as it happens, so it can react to a log or watcher while it runs, including after it went idle. Lines within 200 ms arrive together; a monitor ends when its command exits, after its time limit (5 minutes by default, at most 30) or with `stop_background`, and one that sends more than 20 messages a minute is stopped.
- On Pi, Messaging (a preview, off by default: the Messaging switch in `/freeflow settings`, or `messaging.enabled`) lets the agents in your Pi sessions on this machine send each other plain-text messages: ask one session to tell, ask or answer another, and the reply comes back on its own. A message reaches the other agent after its current tool calls, or starts a turn when it is idle; a session that has had no prompt yet shows it and reads it with your first prompt. A message is information from another agent, never your instruction. Ask before delivering (`messaging.inbound`) can hold messages for you to accept: never (the default), from outside the repository's Task Memory project, every message, or refuse all. Sessions are addressed by session ID and shown by name, and each step is one line in the transcript. The `send_message` tool's description says to read the Messaging skill first.
- Task Memory links each repository in a project, and each child's worktree, to the project's store at `.freeflow/project`, so you can open and edit its records in your editor while the agent works. The link is kept out of Git through the clone's `.git/info/exclude`, and made again at session start when missing.
- Task Memory can remove tasks and projects: ask the agent ("remove the trial project") or run `/freeflow task remove <ID>` or `/freeflow project remove <name>`. A dialog always asks first, names what goes and which Git worktrees stay. Removed records move to `~/.freeflow/trash/`, and only you delete them for good, with `/freeflow trash empty`; the agent cannot. Track Work's CLI has `task remove` and `project remove` for other hosts, and task numbers are never reused.
- Review Work reviews two more kinds of thing: a report or record of work done (a final report, a results note, a Working Record), checked claim by claim against the outputs and files it describes; and an eval definition (a case, suite, fixture or grader), checked before its runs are paid for, for whether a correct answer can pass, a wrong one cannot, and its defects are real. It also adds a judge contract for any model whose verdict on another agent's output is used as evidence: what to record about the judge, what it must be shown, and how to combine verdicts. Before a model reviews anything, the deterministic checks that apply run first, and an adjudicated review is recorded in the task's Working Record.
- Evaluate Behavior can run a subject with Freeflow loaded, built from an exact commit, with repository and personal settings declared in the configuration and checked by that build's own validator before anything runs; comparing two settings, such as Task Memory off and on, is one `component`. `run` prints its plan (subjects, models, Freeflow builds) before starting, and asks on an interactive terminal unless `--yes` is given. Aggregates now count grade errors and run states, report pass^k per check (whether it passed in every trial) and the per-trial pairs per comparison, and name the strongest claim the counts support. A `file-text` expectation can check one `line`, such as a review's first-line judgment.
- `skill-eval review` checks its reviewer against Review Work's judge contract: it shows the reviewer the task's fixture and each run's written files in full, hides run paths and arm names, records the reviewer's model family against the subject's, and with `--swap` reviews again with the runs in the other order to show whether position decided the answers.
- Evaluate Behavior body groups may give the subject Pi's `ls`, `find` and `grep`, confined like `read`: without a path they work in the run's workspace, and a path outside the evaluation environment is refused. A reviewer can then list the files it was given instead of guessing their paths. `bash` and `powershell` stay unsupported.
- An eval configuration declares the host's Pi extensions and settings: `host.extensions` names installed Pi packages by exact name and version (such as an Anthropic subscription's auth extension), and `host.settings` becomes each subject's Pi `settings.json`. Both are recorded with every run and may be the compared component, so a definition can evaluate any Pi setup, not only Pi's defaults. `skill-eval review --configuration <file>` gives the advisory reviewer its model, extensions and settings the same way.
- Evaluate Behavior can run its agents in Claude Code as well as Pi: a configuration with `"host": { "name": "claude-code" }` runs subjects, judges and simulated users in headless Claude Code, with only the declared tools, no settings, instruction files, MCP servers or slash commands from the machine, and the same confinement as on Pi. Bash runs only in a container environment, and the login comes from your environment (such as `CLAUDE_CODE_OAUTH_TOKEN`, which `claude setup-token` prints), never from a copied file. Each run records what Claude Code sent to the model, since Claude Code adds a line about itself and a note about the environment to every request.
- Evaluate Behavior accepts an optional group field `"revision": "description-only"`: before any subject runs, the evaluator checks that the two target skills differ only in their frontmatter description, and refuses the group otherwise.
- A Working Record can hold a Work agreement: an optional `### Work agreement` heading directly after Goal, for what done looks like, what the agent does without asking, what needs your yes first, where it comes back and how long that holds (each line led by `Done when`, `Without asking:`, `Ask first:`, `Back` or `Holds until`), with your reply quoted. `init` writes it only when its input has one, and `validate` rejects it when empty or anywhere else. Records without it stay valid, and nothing is migrated. In a record that has one, return conditions and actions that need your yes move there from Boundaries.
- Verify Work checks changes to existing tests: `test-changes.mjs` lists every test file, fixture, snapshot and shared test setup file that changed, moved or was deleted since a base commit, with the changed hunks, and the agent gives each one a reason (it keeps what the test checked, or follows a behavior change you agreed) or brings it to you before calling the work done; `--new` lists added test files. Its guidance also asks new tests to assert only agreed behavior, names signs of a test too weak to catch a bug, runs a bug fix's regression test on the unfixed code, bounds a speedup by the share of the run that changed, and treats a no-regression claim without a baseline as unproven.
- Write Docs covers a feature map: one file per user-facing feature in the developer docs, saying what the user sees and the exact steps and results that show it working in the running software, plus one shared guide for launching, checking, driving and cleaning up, and which steps cost a model call. When a project with code has no developer docs, the agent recommends creating them and waits for your yes, instead of putting that knowledge in `AGENTS.md` or `CLAUDE.md`.
- Verify Work uses a project's feature map when a claim needs the running software: it finds the feature files that cover the changed code, reads only those, the shared guide and its helper, drives the steps through the saved helper, and when a step fails decides whether the steps drifted, miss the claim, or the product is wrong. A product bug is reported, never written into the steps. Corrected steps are saved with the change when your agreement covers docs, and proposed otherwise.
- Write Docs' docs check gains `--covering <path>`: it lists the documents whose `Covers` header includes each path (the file, or a folder holding it), with the commit each was verified at and whether it is current or stale, so a change can find the docs it should reread. Without document arguments it searches the project's docs index, and it reports how many documents have no `Covers` line.
- Write Docs has a default developer-docs layout for a project that has none (`dev-docs/` with an overview, then `subsystems/`, `features/`, `guides/` and `adr/` as each is needed), proposed to you rather than created; a project with its own docs keeps them, found in the order `dev-docs/README.md`, `ARCHITECTURE.md`, a `README.md` in `docs/`. It also says which kind of knowledge belongs where: developer docs, instruction files, the task's record, or your host's memory.
- Verify Work can set up a feature map: when you want a tested way to check your software live, the agent studies the repository and writes a feature map in your developer docs (one file per user-facing feature, with the exact steps and the results to expect), a shared guide, and a helper script that launches the software in an isolated run, drives it the way a user does, keeps evidence, and cleans up. It drives every step it writes before calling it verified, marks the rest unverified, and later rechecks the map feature by feature when you ask, reporting a product bug instead of editing the steps to pass. Steps that call a model or another paid service run only with your yes, and the helper starts the software without credentials otherwise. Verify Work proposes it when a claim needs the running software and no recipe exists. This lives in Verify Work's feature map reference, not in a skill of its own.
- Evaluate Behavior pipelines can hand a stage's whole workspace to the next: `sees: ["<stage>.workspace"]` starts that stage in a copy of the earlier stage's final workspace, binary files included, so it can run what the earlier stage wrote. `<stage>.files` still delivers written files as text to read.
- Before any container starts, Evaluate Behavior checks that your container engine shares the folder the workspaces live under, and refuses with the folder and the fix when it does not. A VM-based engine such as Colima shares only your home folder by default, so a workspace elsewhere (`check-tasks` uses the system temp folder) used to arrive empty and fail its graders for no visible reason.
- Execute Work covers one mechanical edit repeated across many sites: the agent edits the first site by hand, writes a script or codemod, checks that the script reproduces the hand edit on that site, then runs it on the rest and points to the script in its report so a reviewer can rerun it. A few sites, or sites that each need their own decision, are still edited by hand.
- `skill-author compare` reports what a revision of skills, references, runtime prompts or AGENTS.md no longer says: with no arguments it compares the working tree, uncommitted edits included, with where the branch left the default branch, or two named refs, or a folder copy (`--base`) for text kept outside Git. It lists every bullet, step, table row and sentence that was dropped, moved or reworded, and exits nonzero while a dropped rule (under a Rules heading, a numbered step, or a never, always, must, only, do not or stop sentence) has no verdict in a `--verdicts` file.
