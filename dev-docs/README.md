# Freeflow Developer Docs

> **Covers:** `pi-extension/src/README.md`, `hooks/`, `runtime/prompts/`, `plugin.json`, `package.json`, `command-surface.json`
> **Verified at:** `640b6f9b` (2026-11-07)

For anyone working on Freeflow itself, people or agents: what the parts are, how they relate, the rules that hold across them, and where each part's detailed document is. Using Freeflow is covered by the [user docs](../plugin-docs/README.md).

## Purpose

Freeflow is a feedback-based control system for coding agents (it guides the agent's loop of acting, observing and correcting rather than replacing the agent): a portable skill pack and runtime guidance that steer an existing agent (Codex, Claude Code, Pi and others) through consequential work without ceremony, silent decisions, or unsupported claims. It is not a new agent, a permission system, or an enforcement engine. On Pi it also ships a native extension that adds capabilities the skill pack cannot: Tool Execution (a layer over Pi's tools), Compaction (the agent compacting its own context at a safe point) and Messaging (messages between Pi sessions), all without making a user pay more for the same work than native Pi.

## The Parts

```text
skills/  capabilities/  runtime/prompts/      model-facing methods and guidance (every host)
        │
        ├── hooks/  + host manifests           deliver core guidance at session start (Codex, Claude, Gemini, Cursor, Copilot); Claude Code's mod and Codex's driver
        │
        └── pi-extension/src/                  native Pi delivery and capabilities
              host/            configuration, prompt sections, Runtime State, request history, status, settings
              tool-execution/   compaction/   messaging/        the optional capabilities
              store/           the Freeflow store on Pi: Track Work's script on Pi's events
              events/          the event log and the claims on Pi
              provider-support/                prompt-cache and effort adaptations on qualified provider routes
```

- **Model-facing methods.** `runtime/prompts/` holds the always-present guidance: `core.md` (identity, shared terms, How Freeflow Works: the agree, build, verify, review and return cycle, each step naming the skill that holds its method (Discuss Work at a task's first request, before the first tool call, with the agreement sent before the first change on a task that builds, fixes or changes behavior; Execute Work before the first tool call of any task, read-only ones included, and its delegation reference whenever work goes to another agent; Verify Work before saying a change works, Review Work, Deliver Work, Write Docs, Write Skill before creating or revising text an agent acts on) in the words its description uses, then the references and scripts its routing table gives for common moments (design, simplify, migration, test design, runtime evidence, work and artifact review, branch closeout, delivery state, the docs check), and saying to read that skill's whole body before acting and a reference its table names before acting on that row, that outside the cycle a skill is read when its situation comes up, at any step: Track Work (a Working Record when work spans sessions or a compaction, or the user asks) Evaluate Behavior (before writing or running an eval of a skill, prompt, model or setting) and Research Work (when a question has to be answered from evidence gathered and checked first); what authorizes work and where it stops; reading the project's developer docs and keeping knowledge where it lasts, and recovery after context loss, which a pause or a resumed session that keeps the conversation is not; skills are cued by their own descriptions), `interaction-contract.md` (reading a turn, including a question or a stop mid-work, when to ask, and the Work agreement: proposing it when scope is unclear, ending at its edge with the next step as a question, holding a narrower instruction until the user lifts it, and updating a Working Record's agreement when the user changes direction), `working-method.md` (the rules every task keeps, a one-line habit for each step that names the skill, reference or script holding its method, and keeping tool output small; the full method for each step moved into its skill in 0.9.0) wherever Freeflow is enabled, and on Pi `tool-execution.md` (Pi's tools only; it relies on the Working Method for output and scratch files). `skills/` holds the discoverable skills every host receives; each description says when its skill applies, so the descriptions and core's cycle route the work (Discuss Work, Execute Work, Verify Work, Review Work, Track Work and the rest), and no skill orchestrates the others. `capabilities/` holds one more skill listed only on Pi (`messaging`), not counted among them; the `send_message` tool description names its skill, so the tool leads to it too. How skills route to each other: [Skill routing](subsystems/skill-routing.md). How the prompt is assembled and gated: [Prompt assembly](subsystems/prompt-assembly.md).
- **Host hooks.** Hook-based hosts receive the core prompt, Interaction Contract and Working Method at session start, each unless the user turned it off with `prompts`, and a Runtime State naming the skills the user turned off, through one shared runtime-context renderer and a thin adapter per host (see Host Delivery below). Claude Code and Codex also run a driver (Claude Code's mod, Codex's driver) for the task memory, the event log and the claims. They get no Pi capabilities.
- **The Pi extension.** `pi-extension/src/index.ts` registers Freeflow with Pi and wires every event to its owner. `host/` keeps what is not one capability: configuration, prompt sections, the Runtime State, request history, status and settings. Each capability is optional and lives in its own directory with a subsystem doc: Tool Execution (on by default), Compaction (on by default) and Messaging (off by default). `events/` keeps the event log and the session's claims on Pi, as Claude Code's mod does (see the mod's paragraph below). `provider-support/` changes provider payloads only on qualified routes. [Pi extension](subsystems/pi-extension.md) covers what the extension registers and its persistence limits.
- **Task memory.** Track Work's `skills/track-work/scripts/working-record.mjs` owns the Working Record format and its lifecycle transitions: Schema 5, what `init` writes, and a task folder in the Freeflow store (one Git repository under the Freeflow home that syncs itself) or, without a store, in a repository's Git-ignored `.freeflow/tasks/`. Only `migrate` reads a Schema 4 record, and it moves the record into the store. The skill teaches when to use them. On Pi, `pi-extension/src/store/` runs Track Work's script on Pi's events as Claude Code's mod does (the menu, the sync, the hold, and compaction with the bundle; see [Compaction](subsystems/compaction.md)). Pi's former Task Memory, with its `task_memory` tool, is removed. Track Work's `events append | summary | show` (`lib/events5.mjs`) keep the event log the drivers write, in the Freeflow home's `events/<session>.jsonl`, which the store ignores; each checkpoint and release writes the session's summary into the task folder's `events/<session>.json`, committed with it. How the store and Schema 5 tasks work: [Freeflow store and Schema 5 tasks](subsystems/freeflow-store.md).
- **Tooling.** `scripts/validation/` holds the deterministic checks behind `npm run check`; `scripts/perf/` the request-overhead benchmark; `scripts/release*.mjs` release preparation; `scripts/freeflow-snapshot.mjs` the development snapshot; `.skill-eval/` the current skill evaluation definitions.

## Rules Across The Code

- Freeflow guides; it does not enforce policy. Session hooks only load context, and enforcement hooks stay deferred until evaluations show concise guidance cannot prevent a repeated failure. On Pi, the extension's checks on tool calls (a refused blind overwrite, the bash guard) are working feedback that names the next step, not a permission system.
- One canonical skill tree serves every host. Host manifests point at `skills/`; nothing is copied or generated per host.
- On Pi, Freeflow never makes a request cost more than native Pi would: content a provider cached is never rewritten, the system section and tool definitions stay fixed for a configuration, and generated content is appended. See [Prompt cache rules](guides/prompt-cache.md).
- Freeflow's work on every request and turn stays small and does not grow with session age. See [Performance](guides/performance.md).
- Freeflow never patches Pi, rewrites session files, or replaces Pi's tools; it uses Pi's extension API and appends session entries.
- In the Pi extension, configuration is read only through `pi-extension/src/host/config.ts`; other code receives capability state. Hook adapters read it through the shared renderer, which validates both files with the same `host/config-validation.ts` (built to `pi-extension/dist/`), so a config is valid or invalid on every host alike.
- A failure in an optimization (cache placement, request history replay, compaction additions) falls back to Pi's own behavior; it never fails the user's request.

## Cross-Cutting Concerns

- **Configuration.** `.freeflow/config.json` is the required shared repository activation; `.freeflow/local.json` is an optional personal layer that cannot activate Freeflow alone; a Session scope overrides both without touching either file: on Pi in the Pi session, elsewhere in `<FREEFLOW_HOME>/sessions/<session ID>/settings.json`, which the session-start hook reads over both files. `enabled` is the only core switch. Tool Execution and Compaction are on by default, Messaging off. Removed keys (`defaultMode`, the top-level `interactionContract`, `contextVirtualization`, `conversationHistory`, and `cognitiveRouting` with a message saying the feature was removed) make a configuration invalid, and an invalid file keeps Freeflow from becoming effective rather than falling back to defaults. A `taskMemory` key, left from Pi's former Task Memory, loads and is ignored, and `/freeflow status` says so. Inside Pi subagents all three optional capabilities, Compaction included, stay off. `review` is not a capability: its `unit`, reviewer `model` and `rounds` are read on every host with `resolveReviewSettings()` in `config-validation.ts`, the personal file overriding the shared one field by field, and a non-default choice is one Runtime State line; its `depth` rules are accepted only in the repository's file, and Review Work's `review-plan.mjs` reads them from the base commit of the change it plans, so a branch never supplies the policy that reviews it. How Review Work acts on them is its skill and its scripts. `events.enabled` turns the event log off for Claude Code's mod, Codex's driver and Pi's extension, and `gates.agreement`, `gates.slice`, `gates.delivery` and `gates.delegation` (`off`, `warn` by default, `block`) set each gate for both (`resolveGateSettings()`). `governor.mode` and `governor.cap` are the cost governor's, read by Claude Code's mod alone: their rows say `hosts: "claude-code"`, and `governor.cap` is the table's one number (`values: "number"`, above 0). `delegation.claimHours` (`1`, `2`, `4` by default, `8`, `24`) and `delegation.wakeOnReturn` (on) set how long a claim on paths lasts and whether a returned delegation wakes the waiting session (`resolveDelegationSettings()`, SPEC-009). `prompts` and `skills`, each with a master switch (`enabled`) and a switch per item, are read the same way on every host: Pi leaves an off prompt out and does not load an off skill, and every host's Runtime State names off skills (`skillsStateLine()`). Every key is one row of the settings table (`SETTINGS` in `config-validation.ts`), which the validators, Pi's Session keys, the writes and the settings tests read; a top-level `"v": 1` is accepted and not yet written. Every setting but Claude Code's own has a `/freeflow settings` row on Pi in the Session, Personal and Repository scopes. Outside Pi's screen a setting is changed by Setup Freeflow's `skills/setup-freeflow/scripts/settings.mjs`, which writes through the screen's own code (`config-store.ts`) and prints the Runtime State lines a change gave. User-facing keys and settings: [Using Freeflow](../plugin-docs/using-freeflow.md).
- **Runtime State.** On Pi, current capability state reaches the model as an appended Runtime State message, never as system-prompt changes. See [Request history and prompt cache](subsystems/request-history-and-cache.md).
- **Testing.** `npm run check` is the deterministic gate, including the typecheck (TypeScript strict mode), lint (`eslint.config.mjs`: promises that are neither awaited nor handled, and awaits of values that are not promises, in `pi-extension/src`), manifests, that every host gets the same skills and live text names a removed feature only where `check-hosts.mjs` lists it as on purpose, changelog, docs, formatting, command surface, activation contract, package contents, eval coverage (a recorded skill hash that no longer matches its source fails), that every `.skill-eval` definition loads, the coverage matrix's shape, the skill routing map, and the workflow incident fixtures against their frozen provenance. `npm test` runs every suite, and is what both workflows run: CI runs it as three parallel shards (`scripts/validation/test-shard.mjs`, which deals every suite `npm test` lists to one shard) beside the check gate, and its required "Deterministic checks" job passes only when the gate and every shard did; `format:check` keeps Prettier's content-keyed cache, which CI restores, and `check:source` parses every file in one process with V8 (`macos.yml` runs the Track Work and Pi extension suites on macOS, as a check that does not gate merging: on a pull request only when their code or the dependencies change, and on every push to main; `windows.yml` runs them on Windows on demand, since Freeflow on Pi does not support Windows yet); `check:release-workflow` fails if a `test:*` script is missing from it or CI stops running the shards. Among them, `npm run test:pi-extension` builds and runs the extension suite, including native tests against a real Pi session with scripted model responses; the other `test:*` scripts cover Track Work (with `view recover` and the Material updates pointer audit; its suite runs with the temporary folder reached through a symlink, as macOS's is, by `scripts/validation/with-symlinked-tmp.mjs`, so a path compared with the one Git or the filesystem reports fails on Linux before the macOS job), Discuss Work's `choices.mjs`, Execute Work's `touch-map.mjs`, Deliver Work's `delivery-state.mjs`, `commit-state.mjs`, `release-preflight.mjs` and `push-route.mjs`, Review Work's `check-brief.mjs` and `review-packet.mjs`, Verify Work's `test-changes.mjs` and `self-review.mjs`, Write Docs' docs check (`--covering`), `plan-lint.mjs` and `artifact-check.mjs`, Research Work's shared statistics (`stats.mjs`, checked against published worked examples) and `artifact.mjs`, the snapshot, release utilities and the validation scripts; `test:guards` runs five validation guards (activation contract, package, skill routing, command surface, release version) against a copy of the committed tree, each with one injected defect it must catch. A weekly workflow (`.github/workflows/npm-audit.yml`, as Pi runs daily) audits the installed packages for known vulnerabilities and checks their registry signatures; Freeflow ships no third-party code, so this covers the build tools, and a red run means updating by hand. Model-based skill evaluations are separate and never part of CI; `npm run eval:gate -- --base <ref>` runs the regression suites for what a change touches, locally and on a cheap model (`.skill-eval/scripts/gate.md`).
- **Documentation.** User docs in `plugin-docs/` need the user's approval to change; developer docs here change in the same commit as the behavior they describe. Write both with the [Write Docs](../skills/write-docs/SKILL.md) skill. `npm run check` runs its docs check in strict mode (`check:dev-docs`): it fails when code a developer doc covers changed in a commit that neither changed the doc nor moved its `Verified at` past it, so the doc is reread with every change it covers. `docs-check.mjs --covering <path>` lists the docs that cover a path, so a change can find what to reread.
- **Release.** One npm package, released from a human-pushed `vX.Y.Z` tag. See [Release process](guides/release.md).
- **Development snapshots.** Pi development loads a snapshot of a committed revision built by `npm run snapshot:refresh`, never the working tree: commit first, then refresh. Claude Code's cloud sessions run the commit their environment's setup script fetches; `npm run snapshot:refresh -- --cloud` prints that line for a pushed commit ([Pi extension](subsystems/pi-extension.md#development-boundary)).

## Host Delivery

Freeflow does not ship a CLI, duplicate manifest command handlers, enforcement hooks, or a new agent runtime in this release. It uses each host's native skill invocation and ships one shared runtime-context renderer with host-specific session adapters plus the Pi extension.

- **Codex and Claude Code:** `claude-session-start.mjs` and, on Codex, the driver (below) deliver the core fragments and the Working Method at `SessionStart` (startup, resume, clear, compact and fork). Claude Code runs one hook per prompt because it caps each hook's context at 10,000 characters; Codex runs one hook with a raised `additionalContextLimit`. Codex's marketplace entry installs the npm package, while Claude uses host-valid local source `./`.
- **Claude Code's Freeflow mod:** `hooks/claude/freeflow.mjs`, named under `modules` in `hooks/claude/hooks.json` beside the session-start hooks, is a hooks module Claude Code (2.1.287 or later) runs on its own events. It keeps no memory logic: it runs Track Work's script and delivers what the script prints, and its task memory work runs only where a Freeflow store exists (`session status`, JSON for a harness layer, says so); where `session status` lists something missing for one, it gives the agent that list at session start, with who fixes each part. A store that arrives after session start, as a repository attached to a running cloud session does, is taken up at the first turn end that finds it: the same transcript, pull, repository scan, store permission and take-back session start gives, with one line in the conversation when it takes a task back. Freeflow arriving in a running session is caught up the same way (SPEC-013): the mod keeps, per session, which steps of its session start ran (window, cycle, claims, the store's pull, the menu, the guidance) in `<FREEFLOW_HOME>/sessions/<session>/start.json`, and at a main turn's start a session whose start did not run them (the plugin enabled or updated mid-session, `enabled` switched on, a harness that skips the hook) gets each missing one, once, the guidance and the menu as one row after a line saying Freeflow started mid-session; a step that fails is logged (a `freeflow` event line) and tried once more at the next turn. A normal session, and a reloaded mod whose session's ledger is complete, run nothing for it. Its `prompt.compose` hook adds the session-start hooks' text, rendered by their own renderer (`hooks/shared/runtime-context.mjs section`), as one section of the system prompt (`freeflow:guidance`, after the cache boundary), so it is in every request and the prompt carries it again after each compaction; it is rendered once a session start and once after each `/freeflow settings` change, and the engine sends a changed section only in a new thread or after a compaction. `prompt.section` only rewrites a section the engine itself computes, so it cannot add Freeflow's. At the classic SessionStart the mod leaves the hooks' copies out of the context where the section carries the text: a new thread, `/clear` and a compaction, and a resume or fork only where the ledger says that thread's recorded prompt had the section, since a resumed thread keeps the prompt it recorded. The hooks stay as the delivery wherever the mod does not run. At session start, `/clear` and resume it pulls the store, sets `FREEFLOW_CONTEXT_WINDOW` to the window the conversation compacts against (the model's, or the smaller one `CLAUDE_CODE_AUTO_COMPACT_WINDOW` sets) and `FREEFLOW_TRANSCRIPT` to the session's log, which Track Work's script reads to measure what a Slice uses, and adds `task here --rules --take-back`'s menu and rules to the context, the menu opening with one line when it took back the task this session held when it ended, scanning the session's folder, its siblings and Freeflow's own checkout so the store knows where a task's repositories are. After each request it appends the checkpoint notice, once a cycle, when the context passes the lower of 75% of that window and a tenth of it before Claude's own threshold: keep working to a safe point, then checkpoint with `--compact` and end the turn. Below that point it appends one row showing the context's share at 50%, 60% and 70% of the window, the highest crossed, once each a cycle. The rows and the notice name the context cycle, which the store counts in `sessions/<session>/cycle.json`: every compaction of the main conversation moves it on, and a resumed session keeps it. Both are appended after everything the model already received, so the prompt cache holds (in Phase 6.1's live run, each request after an appended notice read the whole earlier prompt from the cache). At a turn's end it syncs a changed store, and after `checkpoint --compact`, the agent's request and the only thing that makes it compact (the notice now only reminds), it runs `/compact` between turns and submits a prompt to continue, unless a turn started within two seconds of the compaction (input queued meanwhile, which goes on from the bundle, and behind which the prompt would arrive late); the request counts as done only when the bundle has replaced the conversation, so a `/compact` the engine drops (it runs once the session is idle, and a Stop drops it, as when queued input starts the next turn and that turn is interrupted) is tried again at the next turn end, with one line in the conversation saying so, and given up after three drops; it runs the command rather than calling `$.session.compact()`, which passes none of the calling plugin's own hooks, so the engine's summary would stand in for the bundle (a headless session has no turn to come, so its next compaction does it). Every compaction after a checkpoint made in the cycle is answered with `view bundle` as the whole conversation, with no summarizer request; one before it runs Claude's compaction, told what the record holds, and adds `view bundle --fallback` after its summary, or, where the record cannot be read, a message saying how to recover. The store holds the task memory the agent keeps, so its `tool.check` hook lets a file tool (Read, Edit, Write, MultiEdit, NotebookEdit, Glob, Grep) run where the mode would ask when the path's real path lands inside the store's, a path not there yet placed by its nearest existing folder; any deny, a rule's or a hook's, still stands, and nothing outside the store changes. The same hook then runs the [gates](subsystems/gates.md): Track Work's `gates5.mjs` decides the call from the session's `gates.json`, read once a turn and after a Track Work command; under warn the verdict stands and the agent reads one row per gate per turn (a worker, as a message), under block it answers `deny`, or `ask` for a delivery step where an approver is present, and each would-fire is a `gate` line in the event log. It maps a worker to the delegation its Agent prompt names (`sessions/<session>/delegations.json` in the store), sends it the notice near the threshold, once in each of its cycles, adds its delegation to its compaction's instructions, and sends back once a return `delegate check-return` refuses; at session end it releases the hold as ended (`task release --ended`), which a resume of the session takes back. In a worker session (one that ran `delegate join`, SPEC-009), its notice asks for `checkpoint --delegation`, its compaction installs `view bundle --delegation` (after Claude's summary when it came before that checkpoint), and its end runs `release --ended`, which releases its claims and logs that it ended; a session that holds claims releases them at its end too. When a delegation the current Slice waits on has come back (`session status`'s `waits`), the turn end gives one row, `D-NNN returned (done). S-NNN waits on it: check it and close it.`, and where the session is interactive and `delegation.wakeOnReturn` is on, submits it as a prompt after 60 seconds unless a turn started meanwhile, which gets it as a row; while the session sits idle with a delegation still out, it reads `session status` once a minute (`watchWaits`), so a return logged with no turn ending wakes it the same way; it passes `delegation.claimHours` to the script as `FREEFLOW_CLAIM_HOURS`, as Pi does from its capability state (`claimHoursEnvironment`), and several returns found within one 60-second window go out as one row. Its notice to a subagent worker and the block of a worker's stop are each a line in the task's delegation log (`delegate log --append`, `inform` and `blocked`, with the worker's agent ID). It declares `/freeflow` at `session.start` and serves `/freeflow settings` through the settings script, returning its lines as the command's text and the setting with the Runtime State lines that changed as `context` for the model, so a change reaches the agent in the running session. It resolves `enabled` for the session's folder through the same script at session start and after a change; while it is off the mod serves the command and nothing else, and turning it on makes the next turn's start catch up what a session start that ran with it off skipped, or, after one that ran with it on, the next turn end do what session start does with a store. With a store or without, while `enabled` and `events.enabled` are on, it keeps each loop event it sees (session start and end, turns, model requests with their model, effort and tokens, every tool call through a `tool.call` hook, compactions, workers, its own actions) as a schema v1 line, never contents, and writes them with one `events append` run at a turn's end, a compaction, a worker's hand-back, the session's end and before a checkpoint or release command runs, since the mods API cannot append to a file; a failed run drops its lines and the next says how many. At session start, again when `session.start` reports a headless run after them, and when either switch changes, it writes its claims for request set 1 to `<FREEFLOW_HOME>/sessions/<session>/capabilities.json` (a headless run claims no `wake` and compaction only on the next one; with Freeflow off every request is no), and `/freeflow capabilities` runs Setup Freeflow's `capabilities.mjs` on them. Its cost governor (SPEC-014) reads `$.session.usage()` after every model request, the main conversation's and each worker's: on a subscription the seven-day window's daily pace, what was left of it when this day of the window began (counted back from `resetsAt` in whole days, its start kept in `<FREEFLOW_HOME>/events/governor.json` so each session of the day shares it) over the days left from then, against what the day used; with a held task, the high end of its open Slices' predicted cost, read with `estimate --plan --json` at a turn end whenever the task or its last checkpoint changed, against the session's list-price cost since; `governor.cap` puts a percent of the seven-day window in place of the pace, or where there is no window (an API key) dollars of the session's cost in place of the task's cap. At 80% of a cap it appends one row naming the cap, the use and the reset; at 100% one notice under `governor.mode` warn, or under stop the ask to stop at a safe point, checkpoint and ask the user; each once for its cap and period, and each written as a `governor` event line. It decides nothing and blocks nothing. Its tests run with `claude plugin test .` and stand in for the engine and the script; the kit runs no process, so `hooks/tests/golden-events.test.mjs` runs its golden session's lines through the real writer and checks its conformance table; CI has no Claude Code, so the mod's own tests run locally.
- **Claude Code's pane and status line (SPEC-015):** `hooks/claude/pane.mjs`, imported by the mod, keeps one pane, `freeflow`, opened by `/freeflow pane`, and one status line (`$.ui.status`). Its values come from Track Work's JSON, never re-derived: `session status`, `project list --json` and, for the held task, `delegate status --json`, and while the pane is open `estimate --spent --json`, `estimate --plan --json` and `events summary --json`; the context, the session's cost, the plan's windows and the agents from the engine; the context cycle and the worker map from the files the mod keeps in `sessions/<session>/`. It reads on a timer started at session start, at each main turn's end and after a Bash call that ran Track Work's script, so no read sits on the request path, and only where `$.session.surfaces()` names a surface (nothing in `-p` or a cloud session); one read runs at a time. What it read goes into `$.state` (`paneData`, beside `paneView`, `paneSelected` and `paneInput`, declared in `hooks/claude/types.d.ts`, which `.claude-plugin/plugin.json` names under `types`) only when a value changed, so a redraw follows only a change; a script that fails keeps its last value and is named with the time of the last full read. Its `ui.render` hook draws the four views (Tasks, Agents, Cost, Decisions) from `$.state` alone and never writes; Button hotkeys switch views and act. A press runs Track Work's own command through `$.process.run` (`task take`, `task create`, `task move`, `task release`, `delegate check-return`), or `$.ui.view` and `$.session.send` for an agent; one that ran appends one user row saying what the user did, one that failed only shows a toast. Opening a task while this session holds another submits a prompt asking the agent to checkpoint and switch, since only the agent writes a checkpoint (P46). `pane.enabled` and `pane.statusLine` (`hosts: "claude-code"` in the settings table) are read with `settings.mjs list --host claude-code` at `session.start` and after `/freeflow settings` changes one or `enabled`. Its tests are `hooks/claude/pane.test.ts`, with fixture JSON for each script.
- **Codex's driver:** `hooks/codex/driver.mjs <event>`, which `hooks/codex/hooks.json` names on every Codex hook event Freeflow uses, does what Claude Code's mod does where a Codex hook can carry it, each run its own process with the hook's input on stdin. Its session comes from the input's `session_id` (Codex sets no variable), and it runs Track Work's script with `FREEFLOW_SESSION`, `FREEFLOW_HARNESS=Codex` and `FREEFLOW_RESUME=codex resume <session>`, Claude Code's variables removed. What lasts between events is in the Freeflow home's `sessions/<session>/`: `codex.json` (whether `enabled` and `events.enabled` are on and each gate's mode, resolved at session start as the settings script resolves them; whether a store was there; the window; turns; lines a failed flush dropped), `cycle.json` (the cycle as the mod counts it, with its start, notice and highest row), `due.json` (a row or notice waiting), `events-buffer.jsonl` and `calls/` (each tool call's start). At startup, resume, clear and fork (`SessionStart`, 5 s) it renders the guidance, writes the claims, pulls the store (or syncs it when the last session's end left a commit unpushed) and adds `task here --cwd --scan --rules --take-back`'s menu after the guidance; after a compaction (`SessionStart` with source `compact`, 10 s, no context limit) it adds the guidance and the task's bundle after Codex's summary, `view bundle` when the record's State as of is later than the cycle's notice (or its start), else `view bundle --fallback` with a line saying the user's messages since are not in it (no transcript reader), and moves the cycle on. The window is Codex's config (`model_context_window` and `model_auto_compact_token_limit`, the project's `.codex/config.toml` over `CODEX_HOME`'s) or the model's known default; after each completed model request of the main conversation (`PostModelRequest`), the request's `token_usage.total_tokens` against it decides a row at 50, 60 or 70 percent or the cycle's one notice at the lower of 75 percent and a tenth of the window before Codex's limit, kept in `due.json` until the next `PostToolUse` or `UserPromptSubmit` adds it as context (a rename takes it, so one hook delivers it); the notice asks for a plain checkpoint, since Codex compacts on its own. Each event's line is appended to the buffer with no lock; `Stop` (10 s) syncs a changed store and writes the buffer with one `events append`, and `SessionEnd` (3 s, Codex's cap) writes the last lines and runs `task release --ended --no-push`, which commits here only; the next start pushes it. `PreToolUse` (2 s) keeps the call's start time for its line, then the [gates](subsystems/gates.md) decide `Bash` and `apply_patch` calls: it reads `gates.json` once and calls `gates5.decide` (no ask: a delivery step under block is denied); under warn the rows not yet read in this loop's turn (`turn_id`, kept in `gates-warned.json`) go out as `additionalContext`, under block a `permissionDecision: deny` with the gates' text as the reason, and each gate that fired is a `gate` line in the buffer. Every handler fails open: an error prints nothing beyond the guidance and leaves a `freeflow` line with what `error`; the gates alone fail closed while any gate is at block. Its claims (`capabilities.json`, driver `codex-driver`): `pin`, `inject`, `checkpoint`, `block` and `sensors` yes, the rest no. Its tests (`hooks/tests/codex-driver.test.mjs`) drive it with recorded inputs shaped by Codex's generated hook schemas, copied at openai/codex `079e17a4` into `hooks/tests/fixtures/codex/`, and compare a scripted session's log with `hooks/codex/golden-events.mjs`; `hooks/codex/conformance.mjs` names the test for each yes claim. No Codex process runs in them.
- **Gemini CLI:** `gemini-extension.json` and `hooks/hooks.json` with `gemini-session-start.mjs`. Gemini reads an extension's hooks from that path and no other, and Claude Code also reads `hooks/hooks.json` from a plugin's root beside the file its manifest names, so the command names the adapter through `${extensionPath}${CLAUDE_PLUGIN_ROOT}` (each host fills its own, and the other is empty), and the adapter stays silent where `CLAUDE_PLUGIN_ROOT` is set and `GEMINI_PROJECT_DIR` is not.
- **Cursor:** the root `plugin.json` for skills; `.cursor-plugin/plugin.json` adds a `sessionStart` hook.
- **GitHub Copilot and VS Code:** the root `plugin.json`; `com.github.copilot/hooks/hooks.json` for `SessionStart`.
- **Kiro, OpenCode, Hermes and other skills-compatible hosts:** the root Agent Plugins 1.0 package or their skill-source configuration pointing at `skills/`; no always-on prompt surface.
- **Pi:** the root package manifest loads `pi-extension/freeflow/index.js` (Pi 0.99.1 or later).

All hook adapters stay inert without a repository config and never expose Pi capabilities. A config file that cannot be used keeps the guidance on: each setting it ignores keeps its default and is named in the Runtime State (D-045), as Pi's footer and status name it; a missing repository config delivers nothing. Hook trust and registration remain host concerns; local checks prove package and hook shapes, not host dispatch. Per-host detail: [Prompt assembly](subsystems/prompt-assembly.md#host-delivery).

## Review Rules

For anyone reviewing a change to Freeflow, people or agents. Review with [Review Work](../skills/review-work/SKILL.md): its classes, judgments and evidence rules apply unchanged, and this section only adds what is specific to Freeflow. Read it from the base branch, never from the change under review.

- **Blocking Issue in Freeflow:** a change that breaks a Rule Across The Code above; a change to a skill, prompt or other instruction text that does not follow [Write Skill](../skills/write-skill/SKILL.md) or lacks the evidence its claim needs; a changed existing test, fixture or shared test setup (as `skills/verify-work/scripts/test-changes.mjs` lists them) with no reason that keeps what it checked and no agreement from the user; and a claim in a doc, changelog entry or report that the code or an observed run does not support.
- **Already checked:** `npm run check` and `npm test` cover formatting, types, lint, manifests, changelog structure, named doc paths, the command surface and the skill routing map. Run them first, as Review Work's [deterministic checks](../skills/review-work/SKILL.md#before-any-review), and report a failing check, not the findings it would make.
- **Review depth:** Freeflow's review policy is the `review` block in [`.freeflow/config.json`](../.freeflow/config.json), read from the base: every pull request gets a Standard review, never a Quick one, and the built-in triggers make a skill's name or description, a command, a settings key, CI and release files and security changes Deep. `review-plan.mjs` computes it; this section is the reviewer's prose, not the policy.
