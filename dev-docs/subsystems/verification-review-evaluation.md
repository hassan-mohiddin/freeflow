# Verification, Review and Evaluation

> **Covers:** `skills/review-work/`, `skills/evaluate-behavior/`, `skills/verify-work/`, `.skill-eval/scripts/gate.mjs`, `.skill-eval/gate.json`, `.skill-eval/gate/`, `.skill-eval/freeflow-vs-plain/`, `.skill-eval/freeflow-routing/`, `.skill-eval/freeflow-tool-use/`, `scripts/validation/check-eval-definitions.mjs`, `skills/research-work/scripts/lib/stats.mjs`
> **Tests:** `.skill-eval/evaluate-behavior/tests/`, `.skill-eval/verify-work/tests/`
> **Verified at:** `b13ce7db` (2026-10-28)

For contributors changing how Freeflow reviews work, evaluates agent behavior, or verifies claims: what each part does, how they depend on each other, why they are shaped this way, and which of their behaviors are deliberate. It also covers the evaluator's code, the evidence it stores, and the contributor gate that measures Freeflow's own changes.

## Purpose

An agent that writes code also claims things about it: that it works, that a review found nothing, that a change to its own guidance made it better. Freeflow keeps those claims honest with three parts, each answering a different question:

- **Verification** (Verify Work): does this claim hold now, at the boundary where it must hold? It runs checks and says what their results establish.
- **Review** (Review Work): is this work, artifact, report or eval definition correct and complete enough for its use? It judges sufficiency from evidence; it does not create evidence.
- **Evaluation** (Evaluate Behavior and its evaluator): does a declared change to an agent's setup change how the agent behaves? It runs agents under controlled conditions and preserves what they did.

They share one idea: evidence is classed by what observed it, and no class is promoted into another. A passing test is not a review; a reviewer's verdict is not a measurement; a measured difference on one suite is not readiness.

Deliberately out of scope:

- Review Work does not fix, revise, or accept; findings return to the producing activity's owner.
- Evaluate Behavior does not change what it evaluates, claim readiness, or choose adoption; the user decides.
- Model-based evaluation is never part of `npm run check` or CI.
- No part enforces anything at runtime. They are skills: guidance the agent follows, plus the evaluator script it runs.

## How It Works

### The three parts and how they connect

```text
Verify Work ── observes: runs checks, says what results establish
     │  results are evidence for
     ▼
Review Work ── judges sufficiency; owns the judge contract
     │  judge contract governs every model verdict used as evidence
     ▼
Evaluate Behavior ── measures behavior under declared configurations
     │  measured revision target returns to the component's owner
     ▼
Write Skill (skills and other instruction text) / the owner of the component
```

- Review Work's reviewers use Verify Work's check-result and claim-result semantics when they run a covered check; a reviewer that can recover evidence itself, by running an authorized check or reading the code, judges from what it observed.
- Review Work's self-review of work runs Verify Work's `test-changes.mjs` and Test Design's Rule as its test-integrity check, and Verify Work's one-fact line for safety claims points to Work Review's grade of how that fact is known.
- The evaluator's judges, both the pairwise reviewer and rubric judges, follow Review Work's judge contract. Changing the contract is a Review Work change that affects the evaluator (ADR 0013).
- Review Work's eval-definition kind reviews cases, suites, fixtures, graders and rubrics before their runs are paid for.
- Evaluate Behavior measures changes to any component, including Review Work's own wording: the review suite under `.skill-eval/review-suite/` runs Review Work as the subject and scores its reports with rubric judges.
- Write Skill owns skills and other instruction text an agent acts on (instruction files, prompts, tool descriptions, briefs). Its "Evaluate In One Loop" calls Evaluate Behavior to run the arms of a change; Evaluate Behavior returns one measured revision target and never edits the text itself.
- The evaluator's command graders are verification inside an evaluation: hidden tests run against the subject's final workspace.

### Review

Review Work is one skill for every kind of review (ADR 0013). Its core holds the Rules, the three roles, classification, the review gate and the review budget. Four references hold the rest, one per situation: work review (its lenses, the self-review checks, the security risk lens, and the work reviewer's brief and instructions), artifact review (Specs, Plans and other guiding documents, reports and Working Records, and the prompt for any independent review that is not of work), adjudication of a returned review, and evals and judges (eval definition review and the judge contract).

1. **Before a model reviews**, the deterministic checks that apply run first, and their results go to the reviewer as evidence.
2. **Classify before calling something a defect**, in order: is the behavior settled (else a Question); is the claim supported (else Needs evidence); must it be fixed for this boundary (Blocking or Non-blocking Issue); otherwise omit it or name an Improvement. A defect the change did not introduce is Pre-existing: reported for the user, never Blocking. The project's Review Rules (Freeflow's are in the [dev docs overview](../README.md#review-rules)), read from the base branch, feed these classes and the lenses; they never add a class.
3. **Self-review** of work adds two checks (`references/work.md`): a decision check, which Discuss Work owns (its Account At The End lists the choices the agreement did not settle as agreed or for the user in its decision list, `sources/decisions.md` beside a Working Record), and a test-integrity check through Verify Work's `test-changes.mjs`.
4. **The review gate** (the core's "The Review Gate") runs at a hand-over, the end of the agreed work before Deliver Work merges it or opens its pull request, or before the final report, not after each intermediate result. The user's review mode (`review.mode` in `.freeflow/local.json` or `config.json`, shown as a `Review:` line in the Runtime State; `auto` when unset) decides: `auto` dispatches when a trigger fires (security, auth or secrets; data loss or migrations; CI or release files; a public interface; a path the Review Rules mark sensitive; anything the Work Agreement names), `off` proposes the review with its reason and estimated cost and waits for a yes, `always` dispatches every time. The builder records one `Review gate` line through Track Work.
5. **Independent review** is never automatic outside the gate. It is selected by the user or by Review Work's gate at a hand-over, to protect a concrete boundary. The reviewer reports once and stops: Blocking, Inconclusive, Non-blocking or Pass. It edits nothing and adjudicates nothing. It runs what its brief's `May run` line names, by default the project's declared checks (tests, build, typecheck, the feature map's drive steps), in its own copy, with no edits, network calls or paid runs, and only when the builder's saved evidence is missing or does not convince it; Verify Work's rule on active checks counts that line as their coverage, as a request covers its own checks. A work reviewer's brief points to its inputs instead of pasting them: the Working Record, the covering dev docs, the Review Rules, the diff range, the builder's evidence, what it may run, and where to write the report. The reviewer reads them and Work Review's reviewer instructions itself, and `skills/review-work/scripts/check-brief.mjs` refuses a brief missing a line or naming a path or commit that does not exist before it is dispatched. The brief and report are saved in the task's `scratch/reviews/` (`R1-brief.md`, `R1-report.md`, ...), and nothing there is deleted without the user's yes.
6. **Adjudication** by the receiver disposes each finding as Accepted, Rejected or Open, from the actual state rather than the reviewer's verdict. A Rejected security finding goes to the user. One `Review` line per review records the round, reviewer, adjudicated judgment and the Accepted, Rejected and Open counts, so noise and rounds can be counted later.
7. **Budget:** Review 1 broad; Review 2 focused, only when corrections or new evidence need it; Review 3 exceptional and final. Never Review 4. Never repeat a review merely to obtain Pass. Rounds 2 and 3 are briefed with the previous report, its adjudication and the diff since the previous review's reviewed state, never repeat a finding already Accepted, Rejected or fixed, and name a defect's class and where else it occurs. If Review 3 remains Blocking, the builder rethinks the approach.

The judge contract (`evals-and-judges.md`, Judge Contract) is binding for every judge use: record identity (model, provider, family, thinking, prompt hash, date, anything loaded that changes what it is sent); independence and the model relation to the producer (a different model by default, another family optional, the same model only with the reason); what the judge saw and what was withheld; a verdict with evidence, where "unclear" is valid; order and a swap when comparing; the combining rule named before verdicts; calibration, which means a passing judge validation record in Research Work's format (agreement with known answers, both orders for a judge that compares outputs, length control, decoys, repeatability), and otherwise the verdict is advisory. What a judge needs before its answers count is Research Work's (`measurement.md`, Judges); the contract records each use. Rubric judges judge one output alone and blind, so no swap is needed; their combining rule is declared in the definition; calibration belongs to the judge configuration.

### Evaluation: one run, step by step

The evaluator is `skills/evaluate-behavior/scripts/skill-eval.mjs`. `run <suite-or-group>` does this:

1. **Load and validate** (`loadDefinition`). Schema 2 only. Arms are resolved into one effective configuration each (`resolveArms`); a difference outside `component` is refused (`undeclared-difference`), and host name, host version and runtime other than `runtime.environment.literal` may never differ (`unsupported-difference`); a runtime that declares `host` is refused, so `configuration.host.name` is a group's only host. Each known expectation kind's grader runs on the definition alone (`expectationProblems` in `lib/grade.mjs`), so a kind in a group type it cannot grade, an arm or turn the group lacks, a value the grader rejects, or comparison members that are not one check is refused here, and a suite's decision that could only exclude cases is refused too (`decisionProblem`). A suite's refusal names the group and its file. `run`, `check-tasks` and `check:eval-definitions` all load this way, so all of this is refused before anything is spent. `--source <arm>=<commit>` replaces every Git ref an arm declares, for this run only (`applySourceOverrides`).
2. **Check identity** (`lib/identity.mjs`). Every working-tree input must match `HEAD`; otherwise the run is refused unless `--dry-run`. A declared `host.version` must equal the installed host's (`pi --version` or `claude --version`).
3. **Check tasks** (`enforceReferenceChecks`). A group with a `reference_solution` has it applied to a fixture copy and its graders run, before any model call. An unsolvable or already-solved task is refused unless `--skip-reference-check`.
4. **Plan.** Print groups, arms, trials, subjects and reusable runs, and under `unsealed` what will run on the host outside the seal: arms with declared commands or graders there, and each distinct host-extension build (`build-source.mjs`); ask "Start? [y/N]" on a terminal unless `--yes`. Refresh every selected login once (`refreshSelectedLogins`).
5. **Prepare each subject** (`prepareSubject`, then the host adapter's `prepareIsolation` and `prepareLaunch`). Its own `HOME`, temp, `XDG_*` and Pi agent directory under `<arm>/isolation/`; only the declared provider's login copied in, mode 0600, and deleted after exit. Host extensions resolved by exact version; source-built extensions and Freeflow built once per distinct commit. Pi starts with `--no-extensions`, `--no-skills`, `--no-context-files` and the rest, plus the evaluator's guard extension. Claude Code starts headless (`claude -p`, stream-json in and out) with only the declared tools (`--tools`), no setting sources, MCP servers or slash commands, `dontAsk` permissions, and the guard as a PreToolUse hook; its login comes only from the evaluator's environment (`CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY` and the like), never from a copied file.
6. **Confine** (`guard-rules.mjs`, through `pi-guard.mjs` on Pi and the `claude-guard.mjs` hook on Claude Code). Only declared tools; `read`, `ls`, `find` and `grep` resolve inside the declared roots; `write` and `edit` stay in the workspace; declared context files are verified by SHA-256. The default `isolated` prompt mode replaces the host's system prompt with one listing the declared tools, skills and context; `host` keeps the host prompt. `bash` exists only behind a declared, probed shell or a container; in a container environment, `bash` and declared commands both run in the subject's container, which mounts the workspace at its own resolved host path and starts them there, with `workdir` replaced by a link to it (`startContainer` in `lib/container.mjs`), and mounts every other readable root (skills, context, runtime resources, Freeflow's package) read-only at its host path. So `pwd`, the working directory the host reports and the paths its file tools take name one directory, a skill's scripts run from bash by the path the subject was given, and an image's `GIT_WORK_TREE=/testbed` reaches the workspace under the same path, which Git needs to resolve paths from a subfolder. Graders see their copy at `workdir`. Before any container starts, `missingContainerPrerequisites` (`lib/container.mjs`) also reads a marker back through the image from the folder the workspaces live under, so an engine that does not share that folder (Colima shares only the home folder by default) is refused by name instead of grading an empty mount. On Pi, Freeflow's Tool Execution tools run under the same rules. `bash_background` and `monitor` run their command in the container like `bash` (they need a container environment in every arm, refused at load otherwise, since a background command outlives its call and only the container the evaluator removes can hold it); the subject's temp folder, where Freeflow saves their output and names the file to the model, becomes a readable root and is mounted read-only. `apply_patch` is checked like `write` for every path its patch names (`patchPaths` over-approximates Freeflow's parser), and a leading `~` in any path is resolved to the home directory, as Pi and Freeflow do, before the check. The guard decides each shell call but does not rewrite it: `pi-container-route.mjs`, loaded after every other extension, turns the command into the docker client's, so other extensions' `tool_call` handlers (Freeflow refuses a trailing `&` and a long foreground `sleep` in bash) see the command the model wrote; the guard refuses a container shell call if the route is not loaded. Every container command runs through a small wrapper (`containerCommand` in `guard-rules.mjs`): the docker client gets a stdin that stays open while it lives, and when the client is killed (Pi's timeout or abort, `stop_background`, the session ending) the wrapper kills the command's process group in the container, since `docker exec` passes no signal on.
7. **Run** the subject: on Pi, RPC for body groups (`rpc.mjs`) and one-shot JSON mode for description groups. An RPC prompt is sent with `streamingBehavior: "followUp"`, and a run Pi starts with no prompt in flight (an extension's message that starts a turn, such as Freeflow's notice that a background command exited or a monitor printed) is recorded and joins the turn before it (`unpromptedRuns` on that turn); the next prompt, a simulated user's reply and the session's end wait for it; on Claude Code, one stream-json session (`hosts/claude-code/session.mjs`), whose requests pass through a local relay that records what Claude Code sent (`host-context.json`). Conversations and pipelines run several participants (`lib/participants.mjs`). Up to `--jobs` subjects at once (`createLimiter` in `lib/queue.mjs`, which hands a freed slot straight to the next waiter, so a start that arrives meanwhile queues behind it; `--cpu-jobs` bounds local work the same way); budget is reserved before each start and charged after (`lib/budget.mjs`).
8. **Check validity, persist, then grade.** A run the host reported complete that shows no model at work (no assistant message, zero tokens, or no answer and nothing written) becomes `invalid` with its reasons (`lib/validity.mjs`), so graders never start on it. `run.json`, the transcript, events and the workspace are written first. Post-run hooks record metrics (`lib/metrics.mjs`), run command graders on a copy of the workspace (`lib/grade-command.mjs`), and scan the transcript (`lib/scan.mjs`, with `lib/scan-shell.mjs` reading bash commands): reads outside the workspace, declared resources and the arm's own directory (its `isolation/` excepted), network attempts with an external target, instruction files reached outside the workspace, and hidden-test or reference-solution text in the output become `postRun.scan.flags`, over a pipeline's earlier stages too. Deterministic grades and comparisons are written after (`gradeDeterministic`, `gradeComparisons`); an unknown expectation kind or a grader failure becomes `grade-error`, never a changed run.
9. **Aggregate** trials (`runTrials`, `aggregateGroups`): a run with a transcript flag no person has cleared (`clearances.json` beside it, written by `skill-eval clear`) is held, counted as `unavailable` and listed under `held`, and adds nothing to sections or the decision; then per-check counts with pass^k, metrics per arm with paired differences, judged answers, and the decision's verdict. With a decision's `trials` schedule, undecided cases get more trials, up to `max`. An aggregate cut short (by the budget, a stop, or fewer trials than planned) is `cancelled`.
10. **Judge**, as a separate command (`review`), after the evidence exists. `review --rubric` writes judged evidence and rebuilds the aggregate (`rebuildAggregate`).

### Group shapes and modes

The same core runs every mode; a mode is a group shape, with its guidance and its definition fields in one reference (`skills/evaluate-behavior/references/coding-tasks.md`, `conversations-pipelines-judges.md`; compare, noise check and measure in `design-and-measurement.md`):

- **Compare arms:** two or more arms, one reference, a declared component. The default.
- **Noise check:** `component: []` and identical arms; their gap is the floor a real difference must clear.
- **Measure:** one arm, no component, no comparison; yields a rate on the suite. A decision and a pairwise review refuse it.
- **Conversation:** `participants.protocol: "conversation"`; a simulated user answers only from its card, until a stop phrase or `max_turns` (1 to 50).
- **Pipeline:** `participants.protocol: "pipeline"`; ordered stages, each a separate subject that sees only what its `sees` lists (`fresh` stages see nothing earlier). An earlier stage's `response` and `files` arrive as fenced text in the stage's context, to read; `<stage>.workspace` instead starts the stage in a copy of that stage's final workspace, binary files kept, so it can run what the earlier stage wrote (`startingWorkspace` in `lib/participants.mjs`). A stage starts from the fixture or one earlier workspace, never both. The `graded` stage (last by default) is the arm's run; others are stored as `<arm>.<stage>/`. Arms may differ in `participants` when `component` names it, so one review can be compared with two reviews and an adjudicator.
- **Coding task:** the fixture is a repository copied as plain files; `check-tasks` lists what that copy lacks (Git history, ignored files the fixture holds or the task names, tools and network the task refers to) and reports it without refusing; `command` expectations run hidden tests on a copy of the final workspace with grader `files` from outside the fixture; `reference_solution` proves solvability; declared `commands` give the subject `run_command`.
- **Judged evaluation:** a `rubric` of dimensions (`yes/no/unknown` or `0-2`, with an optional judge-only `reference`), `judges`, and `combine` (`majority`, `unanimous`, `any`, `mean`).

### Decisions and claims

A decision names a measure (`comparison`, `metric`, `judged` or `score`), two arms (reference first), a direction, and optionally `alpha` (0.05), `min_cases` (10) and a `trials` schedule (`initial`, `step`, `max`). The unit is the case: each arm's values are averaged over its trials, each case counts as better, worse or equal, and an exact two-sided sign test runs over the decided cases (`signTest`, which `lib/decision.mjs` takes from Research Work's shared statistics, `skills/research-work/scripts/lib/stats.mjs`). `beats` needs at least `min_cases` decided cases, p below `alpha`, and the split in the declared direction; `worse` is the mirror; anything else is `no-difference-shown`. A case whose difference is under one trial's worth is undecided and, with a schedule, gets more trials. The aggregate's claim records the verdict, split, p and the rule's hash (`ruleSha256`). A `cancelled` aggregate reaches no class (`claimFor` in `lib/trials.mjs`): its claim's reason is `cancelled`, the split that ran stays in it, and its `k` is the full trials that completed rather than those asked for; `rebuildAggregate` reaches the same claim from the stored trial states. Without a decision the strongest claim is `rate-on-suite`; "beats" is reported as not supported.

### Judging

- **Pairwise review** (`review --model` or `--configuration`) shows every arm's run side by side under random labels, with paths neutralized, and asks the group's `review_questions`; answers are `yes`, `no` or `unclear`. `--swap` reruns with reversed labels; `--swap-sample <fraction>` does so on a random sample of groups. Stored in `semantic-grade.json`. It is advisory, never calibrated, and not a measure.
- **Rubric judging** (`review --rubric`) has each declared judge answer every dimension for one run alone, blind to its arm, with evidence; answers are combined by the declared rule, and agreement between judges is reported (Cohen's kappa for two, Krippendorff's alpha for more; `lib/agreement.mjs`, which re-exports them from Research Work's shared statistics). Both treat answers as categories; for two judges on a `0-2` dimension, linear-weighted kappa (`linearWeightedKappa`) is recorded beside the kappa as `weighted`, over the runs both scored on the scale, so a near miss counts as partial agreement. Stored per arm in `judged-grade.json`.
- **Fencing:** each judge prompt wraps run material between `BEGIN RUN MATERIAL <token>` and `END RUN MATERIAL <token>` with a fresh random token (`fenceMaterial`). Text inside that tries to direct the judge is quoted back as `steering` and does not change answers.
- **Host setup:** a judge without its own `configuration` inherits the reference arm's host extensions and settings, so it uses the same login and prompt-shaping extension as the subjects. The pairwise reviewer inherits the same way unless `--configuration` is given.
- **Calibration:** `review --calibrate <labels.json>` pairs judge answers with hand labels and records kappa and observed agreement (and, for a `0-2` dimension, linear-weighted kappa as `weighted`) per judge configuration (model, thinking, extensions, settings, rubric hash, prompt version). Re-judging keeps calibration only while that identity is unchanged; until calibrated, answers carry `calibration not checked`.

### The two layers

- **User layer:** `skills/evaluate-behavior/`, `skills/review-work/`, `skills/verify-work/`. Shipped to users, general, with Node and Pi as the only requirements. Nothing in the skill text names Freeflow or this repository.
- **Contributor layer:** `.skill-eval/` (suites, the review suite, the gate and its suites, examples, the evaluator's tests) and `scripts/validation/`. It uses the user layer to measure Freeflow's own changes. One evaluator field is contributor sugar inside the user layer: `configuration.freeflow`, which builds Freeflow from a commit with `scripts/freeflow-snapshot.mjs` in the definition root.

### The contributor gate

`npm run eval:gate -- --base <ref>` (`.skill-eval/scripts/gate.mjs`, guide in `.skill-eval/scripts/gate.md`):

1. Lists paths changed since the base (`git diff --name-only <base>...HEAD`) and matches them against `.skill-eval/gate.json` entries' `paths` globs; each entry names one suite.
2. Prints the plan; `--dry-run-plan` stops there.
3. Runs each matched suite through the evaluator with `--reuse`, `--pilot 3`, the entry's trials, and `--source` mapping the entry's arms to the base commit and HEAD, so the definitions are never edited. Judged suites get an aggregate `review --rubric`.
4. Reports each suite with its aggregate ID and cost: PASS (the decision is `beats` or `no-difference-shown`, or without one, no other arm passed or was judged yes less often than the reference), REGRESSED (`worse`, or some arm passed or was judged yes less often), UNDECIDED (the claim reached no class, a comparison has unavailable outcomes, or the budget ran out first), INFRASTRUCTURE (a refusal, a stopped pilot, or failed, invalid or cancelled runs), or MEASURED (a suite of one-arm groups). Exit 1 if any regressed, else 2 on a refusal or infrastructure failure, else 0.

The gate suites under `.skill-eval/gate/` are written by `.skill-eval/gate/tools/write-gate-suites.mjs` from tuning cases only: `review-work` (6 groups, 12 subjects, 6 judge calls), `write-skill` (7 groups, including three that check Write Skill is chosen for an `AGENTS.md` edit and a tool description and not for a spec), `evaluate-behavior` (2 groups). Their default model is `anthropic/claude-haiku-5-5` at thinking `medium`.

### Freeflow against plain Pi

`.skill-eval/freeflow-vs-plain/` is the standing suite for Hassan's cost rule: success no worse and cost no higher, or a named gain that pays for the extra cost. Ten small coding tasks (bug fixes, one with its symptom in the wrong layer, a README-specified feature, a refactor, a test for a fixed bug, a config tweak, one in Python) each run in two arms on Pi with one shared model (Claude Haiku 5.5 through the subscription's auth extension, both set in the suite's `configuration.json`): `plain` (`freeflow: null`) and `freeflow` (Freeflow built from a commit, Cognitive Routing and Tool Execution off). Every task is a conversation with the same simulated user in both arms (a card per task in `cards/`, on the subjects' model, at most five agent turns): it answers only what the agent asks, says go when asked to proceed, and ends once the agent reports the change made, so an agent that agrees the work before building (Discuss Work) is not graded on a run no one answered. Each task has its own digest-pinned image holding the project's Git history outside the workspace (`GIT_DIR`), sealed with `network: none`; hidden tests are command graders, and behaviour markers (a test that fails before the change, existing tests kept, the fix at the root, a refused `ask_user` call) are reported checks outside the decision, beside judged rubric markers. The rule is declared as two suites over the same groups: `suite.json` decides on the hidden-tests comparison and `suite-cost.json` on the `cost` metric, run after it with `--reuse` at no extra subject cost. It runs only when proposed with its cost and expected decision and the user says yes; its README has the task table, marker map, image build, reading of the verdicts and cost estimate. A later build is measured without changing those suites: `groups-v090/` holds the same tasks with three arms on `configuration-v090.json` (Freeflow pinned at v0.9.0): `plain`, `freeflow` with the same settings, and `freeflow-te` with Tool Execution and its guidance notices on, its tools declared for every arm (Pi's `--tools` is an allowlist, so the arms without them do not get them). Four suites decide success and cost for each Freeflow arm against plain Pi; the first runs every arm and the other three take its runs with `--reuse`. Runs from an earlier host version or evaluator never match a reuse key, so plain Pi runs again with each such change.

### Routing and tool use

Two standing suites measure Freeflow built from any commit, so the same suite measures `main` and a branch through `--source freeflow=<commit>`; both are one `freeflow` arm (Cognitive Routing off, Tool Execution on, Haiku 5.5 through the auth extension, Pi's host prompt, the whole tool set including Freeflow's), in a digest-pinned image with `network: none`, with a simulated user, and neither declares a decision, since one arm has nothing to compare: each has a report script that reads two results side by side. They are the trigger and tool-use evals of the plan to remove the Workflow skill.

- `.skill-eval/freeflow-routing/` asks whether an ordinary request opens the skill that owns it. 93 requests in one fixture repository (`shelf`, whose image holds a branch, a release and an uncommitted change), from the case table in `.skill-eval/freeflow-routing/scripts/cases.mjs`: three per skill for the base's 25 skills and Research Work, added since, and near misses (dedicated ones, and neighbours' requests) for each. A run is at most two turns. Checks are transcript checks on `read` of each expected `SKILL.md` and its absence for each near miss; the report counts reads by `read` or `bash` and gives per skill the hit rate (and on the first turn), the false-trigger rate and what opened instead. Workflow's requests also count Agree Work (the case table's name for Discuss Work, mapped in `MERGED`) and Execute Work as the route, so before and after the removal measure the same route. A skill Freeflow has since removed stays in the case table, mapped to the skill that took over its job (`MERGED` in `cases.mjs`), so later builds are measured on the same requests. The report measures each run on its own build, read from the Freeflow package the evaluator built for the group (`routeCase`): where the build lacks a skill, its owner's read counts as the route, as Workflow's requests count Agree Work and Execute Work; a request whose skill has no owner on that build (Action Selection after its merge, Research Work on a build before it) counts toward no hit rate; and a near miss moves to the owner only while that is still a different skill from the request's route (it is dropped when the owner is the request's own route, a skill the case's `route` names, or a repeat). It reports per measured skill and per owner, so before and after of one current skill read side by side. The groups' graded checks are the same on every build and name both builds' skills, so a check on a skill a build lacks passes or fails by construction; the report is the measure. On a build whose core says to read Discuss Work and Execute Work first (`READ_FIRST`), near-miss checks on those two are dropped, since opening them is what that build asks for; the report reads each build's `core.md` to tell. A near miss counts an open on the first turn only. Cases also name the references and scripts their moment calls for (`parts`, 55 cases); the report counts a reference as used when read like a skill and a script when a `bash` segment that names it runs `node`, maps moved files to their current home (`MOVED_PARTS`), and gives each file's share and the runs that read any reference or ran any script. Parts are graded only in the report, so stored runs can be graded again. Body groups with transcript checks, not description groups: the skills are Freeflow's package, not a declared target, and the change deletes a skill and edits the core prompt.
- `.skill-eval/freeflow-tool-use/` asks whether the agent picks the Tool Execution tool a task calls for, and whether the work gets done: a dev server and its readiness (`bash_background`, `stop_background`), a watcher whose lines need acting on (`monitor`), a three-minute test suite (`bash_background`), a multi-file move with a new file (`apply_patch`) and a one-word fix (`edit`). Hidden tests grade the work (`check-tasks` proves each task in the image); tool-call checks grade the tool, with the alternatives reported. Four script tasks, in their own suite (`suite-scripts.json`, `configuration-scripts.json`, pinned at v0.9.0 with `toolExecution.guidanceNotices` on), ask whether v0.9.0's skill scripts run where their skills say (`self-review.mjs` before the report, `touch-map.mjs` before a shared helper changes, `delivery-state.mjs` before a commit, `choices.mjs agreement` before building on open choices) and whether the guidance notices reach the model (`context-text` checks on the provider context). They share one project, `ledger`, whose history is in its own image, never run on the base build (it has none of the scripts and refuses the notices setting), and have hand-made wrong answers; the report adds order facts read from the sequence of tool calls, such as the script before the first edit. A commit made in a run stays in the subject's container history and ends with it, so the commit is read from the transcript.

### Verification

Verify Work determines what fresh direct evidence establishes about a specific claim at the boundary where it must hold, with references for browser runtime, integration, performance evidence, test design and project recipes. It is unchanged by the evaluator work. The evaluator shares its observing mechanisms (command graders run tests on a workspace; deterministic checks read final state), but Verify Work does not run the evaluator. Verify Work's feature map reference (`skills/verify-work/references/feature-map.md`) builds and rechecks a project's live-verification recipe; the rest of Verify Work uses it.

Verify Work's first page sends a claim about what a user sees to the feature map: the feature files covering the changed code, found with `docs-check.mjs --covering <path> --driven` or listed in Execute Work's self-review report with whether each was driven since its code changed, are driven, and tests settle such a claim only where they exercise that same path. When a claim needs the project's running software, Verify Work's Project Recipe (a section of `skills/verify-work/references/runtime-evidence.md`) has the agent look for the project's saved steps: a feature map in its developer docs, found by the `Covers` header of each feature file, plus the shared guide and helper. It reads only those feature files, the guide and the helper, drives the steps through the helper (extending it when a step is missing), triages a failing step as drift, a gap or a product bug, and never edits the steps to make a failing product pass; corrected steps are saved through Write Docs in the same change, or proposed when the agreement does not cover docs. Write Docs owns the feature file and guide shapes. Verify Work's [feature map reference](../../skills/verify-work/references/feature-map.md) sets a recipe up, after an interview of the repository, and rechecks it feature by feature, driving every step it writes before moving `Verified at`; a failing step is drift, a harness gap or a product bug, and paid calls run only with the user's yes. Freeflow's own map is [Features](../features/README.md), driven with [Verify live](../guides/verify-live.md).

Verify Work's script, `skills/verify-work/scripts/test-changes.mjs`, lists every test file, fixture, snapshot and shared test setup file that existed at a base and changed, moved or was deleted by a head (the working tree by default), with the changed hunks. Test Design's one Rule has the agent give each listed change a reason (the property is preserved, or the user agreed the behavior change) or return it to the user before reporting the work done; Verify Work's body links the script from its Test Design route. With `--new` it lists instead the test files added since the base (committed, or untracked in the working tree); Execute Work's `self-review.mjs` uses both lists and runs each new test on the base in a temporary worktree, so a new test that already passes there is shown.

Review Work's `review-packet.mjs` writes the work reviewer's pointer brief: it fills every line it can from the repository and the task folder (the diff since the previous review's reviewed state for Review 2 or 3, the developer docs covering the changed files through Write Docs' `docs-check.mjs --covering`, a `REVIEW.md`, the declared npm checks), leaves the Boundary and anything it cannot find empty so `check-brief.mjs` refuses the brief until the initiator fills them, and reports the gate triggers the changed paths show and the round budget.

## Decisions

- **One review skill with kinds, and it owns the judge contract.** Review Artifact was merged into Review Work; new review kinds are references, not skills. A judge is a reviewer, so the contract lives with review, and the evaluator is one consumer. Rejected: separate skills per kind (every rule change made twice and drifted); the contract in the evaluator (other judges would restate it). Source: ADR 0013.
- **No reviewer panels, votes, or mandatory different-family reviewer.** The review research found that combining verdicts mostly trades false alarms for detection, identical-model repeats add nothing, and a different family changes what is flagged without a measured gain. Repeated calls to one configuration count as one vote. Source: ADR 0013.
- **Skill names keep verb-object form: `review-work`, `evaluate-behavior`, `verify-work`.** Bare verbs collide with host commands (`/review`); role nouns (reviewer, evaluator) collide with Freeflow terms and read as personas. `evaluate-skill` became `evaluate-behavior` because its subject is any declared configuration, not only skills.
- **Schema 2: the configuration is the subject.** Definitions declare a task plus a configuration with per-arm overlays and a declared component, instead of skill-shaped fields. Optional v1 fields would have made v1 a v2 in disguise.
- **One host-neutral core, one adapter per host.** A host is the agent program that runs the subject's model and tools; a provider serves the model. Everything that depends on the host program (its arguments, events, sessions, isolation and login, extensions, model calls and the shell probes' launch) is in its adapter under `lib/hosts/`, behind one interface (`lib/hosts/index.mjs`); the core (`lib/subject.mjs` and the rest) never names a host. A group's host is its configuration's `host.name`, shared by every arm. Rejected: one adapter per provider (Pi already serves many providers, and one host's flags and events are the same whichever provider serves it).
- **Claude Code runs with its loaders off, and what it adds anyway is recorded.** Claude Code cannot be told to send only the evaluator's prompt: it adds an identity line and an environment note to every request. Its skill, settings, instruction-file, MCP and plugin loaders are off, declared skills reach it as on Pi (a listing in the system prompt, and Pi's exact skill-command text for a body run's target), and a local relay records each request (and the method and path of any other call Claude Code makes to the API host), so a run shows exactly what the model received. Bash runs only in a container environment, since no isolation extension exists for Claude Code; Pi extensions, declared commands and Freeflow are refused at load. Rejected: running subjects as Agent-tool subagents, which inherit the parent's instruction files.
- **Everything that can change behavior is declared.** Host extensions (such as a subscription's auth extension, which reshapes the system prompt) and host settings are configuration, not command-line flags, and may differ between arms. The evaluator's own Pi defaults (`retry.enabled=false`, `compaction.enabled=false`) are merged under declared settings in one place (`effectivePiSettings`), for subjects, simulated users, judges and reviewers alike. Logins refresh centrally through the installed Pi rather than being refused near expiry.
- **Canonical evidence comes from commits.** Working-tree inputs that differ from `HEAD` refuse a canonical run; a dry run is allowed but never enters a claim or the reuse index. This makes every result recoverable from a commit.
- **Judged evidence is its own class.** Judge answers never change run or deterministic grade files; they are stored apart with identity and calibration, and count toward a claim only through a decision declared before the run. Rejected: judges kept purely advisory (rubric scores could not be measures), and judges writing into grades (one class silently promoted into another).
- **The sign test first, with the case as the unit.** Trials of one case are repeated draws of one question, so they are averaged rather than counted as independent. The sign test is conservative and assumption-light; other methods (such as a paired bootstrap) can be added later.
- **Validity by tokens, not by cost or tool use.** A failed login graded "ok" across a whole BtW batch; the gate makes a hollow run `invalid` instead. Cost is zero for real work on an unpriced model, so tokens are the signal; requiring tool use would make every one-answer run invalid, including a description run whose target did not activate, which is the behavior such a run measures. Rejected: the literal spec rule of "more than one turn or real tool use".
- **A flag holds a run until a person clears it; the scan never fails one.** Its patterns are heuristics with false positives (a fixture can name `AGENTS.md`; a legitimate fix can match a reference line), so a flag is evidence to read, held out of claims rather than graded. They are tuned on stored runs so honest work stays unflagged: a network flag needs an external target in a command (loopback, `0.0.0.0`, `localhost` and `*.localhost`, and a URL in a payload or in tool output are not attempts; a host name with no dot is, since it can name a host on the user's network such as `http://intranet` as well as a container's service, so more runs are held for a person to read (2026-10-27)), an install counts only when the run's network was `none` and it names a registry package, the arm's own directory and the temp directory's scratch files are not outside, and an answer copy needs a block of distinctive lines (imports, short lines and scattered idioms are what any code shares). Rejected: flagging on any URL or network word, which held most honest runs that start a local server. A clearance is a separate file with the person's reason, so canonical run evidence never changes, and clearing rebuilds the aggregates that list the run. A pilot stops on an uncleared flag, as it does on an invalid run. Rejected: dropping flagged runs (the evidence would vanish), and letting the agent clear them (the Rule says only the user decides).
- **What the definition alone decides is refused at load, by the graders' own checks.** Each known kind's grader runs with no run evidence when the definition loads, so a check that loads always grades and the rule has one owner; `check-tasks`, `run` and `check:eval-definitions` all load through `loadDefinition`, so the refusal comes before any spend on every path. Before, a body-only kind in a description group, an undeclared turn or a bad value became a `grade-error` after the subjects were paid for. Rejected: checking only in `check-tasks` (a `run` or `check:eval-definitions` would still pass it), and a second validator beside the graders (two owners that drift).
- **A decision is refused at load only when it could only exclude cases.** A group without a decision arm, a group that records the measure in one decision arm but not the other, an unknown metric, or a measure no group records in both arms is refused. A group that records it in neither arm loads, and its case is excluded and counted: the review suites and the `.skill-eval/agree-work/` suite mix in control cases with no rubric or no hidden tests on purpose. Rejected: requiring every group to record the measure.
- **Deterministic first.** A judge answers only what checks cannot. Command graders, reference solutions and the ten expectation kinds carry as much as they can before any model judges.
- **No required dependencies; optional ones only when declared.** The user layer runs on Node and Pi. A confined shell needs a declared isolation extension (such as the Gondolin example) and a container needs the `docker` CLI; each is checked only for a group that declares it. When something is missing, the evaluator refuses with what is missing and how to install it, and the skill tells the agent to ask the user before installing. Images are pinned by digest and never pulled.
- **One network policy for all code the subject wrote.** `configuration.network` covers bash, declared commands and command graders alike (`lib/seal.mjs`). `"none"` is refused at load unless every such path is confined (bash by a probed shell or container, commands and graders by the arm's container), and each run records `sealing`. Without a declaration the arm gets what its paths allow, so existing definitions whose declared commands run `node --test` on the host keep loading; the plan names unsealed arms, and the host-extension builds that run on the host before any subject. A declared command on the host gets no `PI_CODING_AGENT_DIR` or login variable. Rejected: a named host allowlist for now (Docker needs a user-defined network and an egress proxy, which nothing here verifies); refusing unsealed host commands by default (would break the Work Agreement suites until they declare `"host"` or move to an image).
- **A shell is allowed only as verified confinement.** Six probes run through the arm's own host (Pi, or Claude Code) before any subject: a workspace write that must succeed, and a write outside, a read of the home's parent, a read of a marker in the host's login directory (the adapter's `loginDirectory`, Pi's agent directory), a network call and an environment leak that must all fail. A run's `sealing.login` is `out of reach` with bash only when the login probe held. Rejected: trusting an isolation's claims without probing.
- **One-arm measure groups.** Recording a baseline, scoring a benchmark and regression checks need a rate without a comparison; a one-arm group is its own reference and can never support a comparison claim.
- **Judges inherit the subjects' host setup unless they declare their own.** A judge launched without the subscription's auth extension was refused by the provider as unbilled extra usage; inheritance makes the default correct, and a declared `configuration` lets a judge differ on purpose.
- **Reuse by content, not by name.** `--reuse` counts an indexed complete run as a trial only when a hash over the task, group inputs, the arm's effective configuration and inputs, model, host version and the evaluator's own code matches, and never a run held for uncleared transcript flags. Rejected: reusing by result ID or commit alone, which cannot tell that a grader or the evaluator changed.
- **The cost rule as two decisions over one set of runs.** A decision takes one measure, and the rule has two (success and cost), so the standing suite declares both before any run as two suites over the same groups; the second reuses every run of the first. Rejected for now: a decision with several measures, which would change the decision schema for one suite.
- **The standing suite turns Freeflow's Tool Execution off.** It was defined, and its first runs made, while `bash_background` would have run on the host and `apply_patch` outside the guard's path checks; left on but undeclared, its prompt would steer the model into refused calls. Since 2026-10-22 the evaluator confines those tools in the container, and the routing and tool-use suites run with Tool Execution on; turning it on in the standing suite is a change to that suite's measure, to decide with its owner.
- **Freeflow's background tools run only in a container.** A background command outlives the call that starts it, so only a container, which the evaluator removes when the subject ends, can hold it; a shell isolation extension wraps only `bash`. The container route runs last so Freeflow's own refusals of shell habits still see the command the model wrote, and the lifetime wrapper makes stopping a command on the host stop it in the container, as Pi's own kill of the process group would on the host. Rejected: setting Pi's `shellPath` to a container shell (every shell spawn, including the monitor's redirect of stderr to its host output file, would run in the container) and refusing the tools (the tool-use eval needs them). `ask_user` stays on and is refused by the guard (Pi's RPC mode would wait for an answer the evaluator never sends), and the refused call is a reported marker.
- **The gate is local, not CI.** It calls real models, needs the contributor's credentials, and costs money; `npm run check` stays deterministic. The gate measures each change base against head on a cheap model with reuse, so later autonomy work can call it.
- **Point, don't paste, in a work reviewer's brief.** In the R-a trial (135 Grok 4.7 reviews over the review suite, 2026-10-21), a brief pointing to the inputs found the same 27 of 30 seeded and real defects as the full pasted prompt, at about 16% lower cost per review ($0.40 against $0.48), and rejected 7 of 15 clean changes against 6. The audit of those rejections tied the extra one to a reviewer misreading the code, not the brief, and the trial's tests command was broken for every arm alike. Artifact reviews keep the pasted prompt: the trial measured work only. Rejected: "judge first, then read the builder's evidence", which showed no difference (one decided case).
- **References by situation, one owner per rule.** Each skill keeps a core that is enough for the common case and a few larger references, each one situation read together; a rule is stated once and pointed to elsewhere. The one deliberate copy is the non-work reviewer prompt in `artifact.md`, which carries its own classification and judgment because it is pasted to a reviewer that reads nothing else of the skill. Rejected: one reference per kind and per lens (nine in Review Work, seven in Evaluate Behavior), which repeated the ladders and lens lists and sent readers through many small files.
- **A review's `May run` line is coverage for active checks.** Verify Work runs a test, build or other active check only when it is covered; a request covers its own checks (core), and an independent review covers what its brief names, by default the project's declared checks in the reviewer's own copy with no edits, network calls or paid runs. Before, Verify Work required agreement coverage while Review Work let reviewers run "read-only" checks by default, and tests are not read-only.
- **`test-changes.mjs` lists and never judges.** It answers which existing checks changed, which an agent can miss in its own work (a shared fixture edited to make broken tests pass, reported as "Fixed"); whether a change is justified stays with the agent and the user. It matches paths, not content, with case-sensitive defaults for common layouts in JavaScript, TypeScript, Python, Go, Ruby, Java, Kotlin, C#, Swift, C and C++, PHP, Elixir and Dart, and `--pattern`, `--only` and `--exclude` for the rest. Tests inside source files (Rust's `#[cfg(test)]`, doctests) have no path of their own and are not listed; reading content to find them would turn a listing into a judgment. Git runs with fixed flags (`--no-color`, `--no-ext-diff`, `--no-textconv`, `--no-relative`, `-M`, fixed prefixes) so the user's diff configuration cannot change the listing. Rejected: failing on any test change, which refactors and agreed behavior changes would trip and agents would learn to argue past; detecting setup hooks from the changed lines, a partial signal that would read as "no setup changed".
- **Prefer measuring before adopting guidance.** Review Work's evidence sentence was adopted after it raised clean-change acceptance from 77% to 91% with detection unchanged; a second candidate sentence was dropped because it lost guard bypasses (`.skill-eval/review-suite/results/`).
- **Agree Work is Discuss Work.** Decision Gate was renamed Agree Work on 2026-10-21, and Agree Work merged into Discuss Work (`b766519`). The routing case table and the `.skill-eval/agree-work/` suite keep the old name.
- **Map Features is Verify Work's feature map reference.** Map Features set up and rechecked a project's feature map, guide and helper until it merged into Verify Work on 2026-10-24 as `references/feature-map.md`, with Driving Surfaces as a section of it.
- **The routing report counts a near miss's open on the first turn only.** The simulated user's "go" on the second turn can ask for the work the near miss left out (2026-10-24).

## Intended Behavior That Looks Wrong

- **`--dry-run` still runs subjects and calls models.** A dry run only allows uncommitted inputs and keeps the result out of claims and the reuse index. To check that definitions load without spending, use `npm run check:eval-definitions`; to check a coding task, use `check-tasks`. Making dry runs skip subjects would remove the only way to try an uncommitted candidate.
- **An unknown expectation kind passes loading.** The ten known kinds are checked at load by their own graders; an unknown kind fails at grading as `unsupported expectation kind`, recorded as a grade error, and so does a comparison it belongs to. Grading errors are evidence about the definition and never rewrite the run.
- **The gate suites declare no decision.** A sign test needs at least six decided cases in one direction to reach p < 0.05, and the gate's review suite has three judged cases. The gate reads per-comparison and per-dimension counts instead: any arm passing less often than the reference is REGRESSED.
- **A `fail-to-pass` transition is not "better".** Transitions are factual comparisons from the reference; only a declared decision says which arm is better.
- **Reuse misses after any evaluator change.** The reuse key includes a hash of the whole `scripts/` directory and of the shared statistics it imports (`skills/research-work/scripts/lib/stats.mjs`), so subjects rerun when the evaluator or its statistics change even if nothing else did. Reusing across evaluator versions could pair runs graded or isolated differently.
- **`--trials` must equal a decision's `trials.initial`, and `--variant` is refused for a decision suite.** A decision compares two arms over a schedule declared before the run; overriding either would make the rule something chosen at run time.
- **A pairwise review is never calibrated.** It compares arms side by side for reading, not measuring; calibration applies to rubric judges.
- **The isolated prompt replaces the host's system prompt.** It removes ambient instructions so only declared context reaches the subject. When the component is something the host prompt carries, such as Freeflow, the group declares `runtime.prompt: "host"`.
- **A judge's answers count as one vote however many times it runs.** Repeated calls to one configuration are not independent judges.
- **`test-changes.mjs` exits 0 when it lists changes, and lists a new test file only with `--new`.** It reports and does not gate (see Decisions). A file that did not exist at the base is a new test, not a changed one; whether it asserts agreed behavior is Test Design's judgment. Against the working tree, a moved file that is not staged shows as deleted, because Git pairs renames only between tracked files.

### Definition keys

The binding shape is `skills/evaluate-behavior/references/authoring.md`, with each mode's fields in its mode reference. Rules the loader enforces with an error that names the field are not restated there: the references point to `check-tasks` and keep only what its errors cannot teach (meanings, defaults, choices, and the few rules needed while designing a group). In summary:

- **Suite:** `id`, `groups`, optional `decision` (`measure`, `arms`, `direction`, `method: "sign-test"`, `alpha`, `min_cases`, `trials`).
- **Group:** `id`, `type` (`description` or `body`), `input` (`prompt` or `turns`, plus optional `resume_before` on Pi body groups with a persistent session: before each named turn the RPC session is closed and resumed from its own file through `switch_session`), `fixture`, `tools`, `configuration`, `arms`, `expectations`, `review_questions`; optional `component`, `commands`, `revision: "description-only"`, `reference`, `rubric`, `judges`, `combine`, `reference_solution`, `participants`.
- **Configuration** (group, arm overlay, or a file via `extends`): `host` (`version`, `extensions`, `settings`), `model`, `subject` (skills, target, source, context), `freeflow`, `runtime`, `shell`, `environment`, `network`, `participants`.
- **Expectation kinds:** `skill-read`, `resource-read`, `path`, `changed-paths`, `file-text`, `json`, `response-text`, `context-text`, `tool-call`, `command`.

```text
      deterministic-grade.json        checks, comparisons, grade errors
      group.json                      states, reused runs, artifacts
      semantic-grade.json             pairwise advisory review
      review/, review-swap/           the reviewer's prompt, events and output
      judging/<token>/judge-N/        rubric judges' scratch directories
      resources/                      snapshots of fixture, skills, context, runtime, Freeflow, extensions
      confinement/<arm>/confinement.json
      commands/<expectation>/         command-grader workspace copies
      <arm>/run.json                  the subject's record, metrics, sealing, post-run commands, participants
      <arm>/transcript.json, final.md, events.jsonl, stderr.log, context-observations.jsonl
      <arm>/workspace/                the subject's final workspace
      <arm>/judged-grade.json         judged evidence
      <arm>/clearances.json           a person's clearances of transcript flags, with reasons
      <arm>/isolation/                HOME, agent dir, tmp; copied logins removed after exit
      <arm>.<stage>/                  pipeline stages other than the graded one
  <aggregate-id>/aggregate.json       per-check counts, pass^k, metrics, judged, decision, claim, held runs, each trial's cost, budget; trials are sibling directories
```

- Everything is on disk; nothing lives only in memory between commands. `rebuildAggregate` rereads every trial's `summary.json` and grades and rewrites `aggregate.json` (sections, decision and claim), keeping its ID, trials, schedule and budget. It runs after rubric judging and calibration of an aggregate.
- Calibration is stored in each judged grade's `judges[].calibration`: state, agreement, kappa per dimension (with `weighted`, linear-weighted kappa, for a `0-2` dimension; calibrations recorded before it have no such field), the labels file's path and SHA-256 (the labels are not copied), and when it was checked.
- Every canonical invocation writes `index.jsonl`, with or without `--reuse`, for its complete, graded, non-reused runs; dry runs never do. Only `--reuse` reads it.

## Invariants

- Run evidence is written before any grade, and no grade or judge ever modifies `run.json`, the transcript or the workspace. Guarded by `grade-command.test.mjs` (graders run on a copy) and `judge.test.mjs`.
- Judged evidence appears only in `judged-grade.json` and pairwise answers only in `semantic-grade.json`; neither is in `deterministic-grade.json`. Guarded by `judge.test.mjs`.
- Rubric questions, rubric references, grader files and review questions never reach the subject. Guarded by `judge.test.mjs` (the rubric never reaches the subject) and `grade-command.test.mjs` (grader files come from the definition directory, not the fixture).
- Arms differ only in their declared component. Guarded by `arms.test.mjs` and `definitions.test.mjs`.
- A known expectation kind that loads is accepted by its grader, and a suite's decision that loads can read a value from at least one case. Guarded by `definitions.test.mjs` and `decision.test.mjs`.
- A canonical run has no uncommitted inputs, and a declared host version matches the installed Pi. Guarded by `identity.test.mjs`.
- Each subject has its own home, temp and agent directories, and only its provider's login, removed after exit. Guarded by `isolation.test.mjs`.
- A subject's tools stay inside declared roots, and `bash` exists only behind a probed shell or a container. Guarded by `pi-guard.test.mjs`, `shell.test.mjs`, `container.test.mjs`.
- A link in a subject's workspace is recorded with its target and never followed, in the run, a pipeline handoff and a grader's copy; a declared resource or fixture may hold only relative links inside it, copied as they are (`fingerprintDirectory`'s `links` option). Guarded by `grade-command.test.mjs` and `participants.test.mjs`.
- Every reader of a file the subject wrote (the judge's and reviewer's evidence, the HTML view, the transcript scan) opens it through `lib/subject-file.mjs`: never through a link, only a regular file whose real path is inside the workspace, and at most a bounded number of bytes; a skipped file is named with why. Guarded by `review.test.mjs`, `view-html.test.mjs` and `scan.test.mjs` (a link to a secret, to `/dev/zero` and to a FIFO).
- In a container environment, the subject's `bash` and declared commands run in its container and graders in a fresh one from the same image. Guarded by `container.test.mjs` and `command-tool.test.mjs`.
- Freeflow's `bash_background` and `monitor` run only in the subject's container, `apply_patch` writes only inside the workspace, and a command stopped on the host stops in the container. Guarded by `container.test.mjs` (the route runs last, refusals, patch paths) and `tool-execution-container.test.mjs` (real Pi, Freeflow and engine with a scripted model; skipped without them).
- A run Pi starts on its own between prompts is recorded in the turn before it and never ends the session as a protocol error. Guarded by `rpc.test.mjs`.
- A container subject's `bash` starts in the directory its host reports as the working directory, and a file one of the host's file tools writes there is the file `bash` reads at that path and at `workdir`, and the reverse. Guarded by `container.test.mjs`.
- A declared `network: "none"` holds on every path that runs subject-written code, or the group is refused at load; every run records `sealing`. Guarded by `container.test.mjs` and `grade-command.test.mjs`.
- Every model the evaluator launches (subject, simulated user, judge, reviewer) gets the evaluator's Pi defaults under its declared settings. Guarded by `isolation.test.mjs` and `review.test.mjs`.
- "beats" is reported only from a declared decision, and never from an aggregate cut short. Guarded by `decision.test.mjs` and `trials.test.mjs`.
- A missing metric is `null`, never 0, and a run that is not complete adds no metric to a summary or decision. Guarded by `metrics.test.mjs` and `decision.test.mjs`.
- `peakContext`, `skillReads` and `skillReadTokens` come only from a Pi transcript (null elsewhere); skill reads count every successful read of a declared skill's files or of the loaded Freeflow package's `skills/`, `capabilities/` and `runtime/`, re-reads included, at an estimated 4 bytes per token, and an arm with neither reads 0. Guarded by `metrics.test.mjs` and `freeflow.test.mjs` (a fake Pi reading the built package's skill).
- A complete run that shows no model at work is `invalid`, never graded as a fail. Guarded by `validity.test.mjs` and `trials.test.mjs`.
- A run with a transcript flag no person has cleared counts toward no claim or decision, and clearing never changes the run's files. Guarded by `held.test.mjs` (checks, comparison arms, pairs and transitions, metrics, scores, judged answers and every decision measure), `scan.test.mjs`, `trials.test.mjs` and `participants.test.mjs`.
- No more than `--jobs` subjects (and `--cpu-jobs` local tasks) run at once, even when a start arrives while a freed slot passes to a waiter, and parallel subjects cannot overshoot `--max-cost` by more than the running set. Guarded by `concurrency.test.mjs`.
- The evaluator never pulls an image and never installs anything. No test can prove an absence; `container.test.mjs` and `shell.test.mjs` check that missing prerequisites refuse.
- No test calls a real model: tests use `helpers/fake-pi.mjs` and `helpers/fake-docker.mjs`.

## Failure Behavior

| Failure | Result |
| --- | --- |
| Undeclared difference between arms, unknown key, schema 1, a runtime `host`, an expectation its grader would refuse, a decision that could only exclude cases | Refused at load, naming a suite's group and its file; nothing runs |
| Uncommitted inputs | Refused, naming the paths, unless `--dry-run` |
| Host version or extension version mismatch | Refused before anything starts |
| Login under 30 minutes and refresh fails | Refused: log in again in Pi |
| Reference solution fails, or the task is already solved | Refused unless `--skip-reference-check`; `check-tasks` exits 1 |
| Shell prerequisite missing (such as QEMU for Gondolin) | The arm is invalid; the message names what is missing and says to ask the user before installing |
| A confinement probe holds when it should fail | The arm is invalid: "is not confined" with the probes |
| Docker missing, daemon down, image absent | The group is invalid before any subject; an absent image gets a `docker pull` suggestion, never a pull |
| Subject protocol error, extension error, changed immutable resource | `infrastructure-failed` run |
| Host exits cleanly but no assistant message, zero tokens, or no answer and nothing written | `invalid` run with `error.reasons`; graders do not start; a pilot stops |
| No progress for 30 minutes | `no-progress-watchdog` ends the subject |
| Budget reached | Remaining subjects are `cancelled` before execution; overshoot is recorded; a decision's claim reaches no class (`cancelled`) |
| Unknown expectation kind or grader failure | `grade-error` evidence; the run stays as it was |
| Transcript flag not cleared | The run is graded but held: `unavailable` in the aggregate, out of the decision; a pilot stops |
| Judge exits early, returns non-JSON, or misses a dimension | `judge-error` for that grade; other grades unaffected |
| Pilot finds a problem | The batch does not start; no aggregate is written |
| Unreadable trial during `rebuildAggregate` | Refused rather than counted as passing |

## Cost

- Subject runs are the cost. Reduce them in this order: answer from saved evidence; `check-tasks` (no model); `--pilot`; `--reuse` from the first batch so unchanged baselines are reused; a decision's adaptive `trials` schedule; fewer judge calls (deterministic checks first, `--swap-sample`, the smallest view a question needs).
- `--jobs` saves time, not spend. `--cpu-jobs` keeps local work (graders, builds, probes) within what the machine carries.
- `--max-cost` bounds the host's list-price estimate. On a subscription the binding limit is the plan's usage, which the evaluator cannot see; the plan line's subject count is the figure to check before a large batch.
- Each run records `cacheHitRate` and token counts per subject, so prompt-cache behavior is visible per arm.
- Measured on 2026-10-12: one gate smoke run on Haiku 5.5 with the auth extension ran 6 Review Work subjects base against head and 6 rubric judges; review subjects cost about $0.40 each at list price.

## Tests

`.skill-eval/evaluate-behavior/tests/` has 38 test files, run by `npm run test:skill-eval` with a fake Pi (`helpers/fake-pi.mjs`) and a fake Docker (`helpers/fake-docker.mjs`):

- **Definitions and arms:** `definitions`, `arms`, `measure`, `source-override`, `entrypoint`, `check-eval-definitions`.
- **Execution and isolation:** `run`, `isolation`, `identity`, `pi-guard`, `rpc`, `command-tool`, `concurrency`, `participants`, `freeflow`, `build-source`, `claude-code`.
- **Environments:** `shell` (probes, refusals, the Gondolin example; the real micro-VM case is skipped without QEMU), `container`, `tool-execution-container` (Freeflow's tools through real Pi in a real container with a scripted model; skipped without Docker, a local image, Pi or `npm ci`).
- **Grading and tasks:** `grading`, `grade-command`, `reference`.
- **Measurement:** `trials`, `decision`, `metrics`, `validity`, `scan`, `freeflow-vs-plain` (the standing suite's decisions and arm shape), `freeflow-routing` and `freeflow-tool-use` (each suite's shape, its report on known runs, and one group as a stub dry run through `.skill-eval/evaluate-behavior/tests/helpers/suite-stub.mjs`: a copy of the suite with stand-ins for Freeflow's build, the auth extension and the simulated user).
- **Judging:** `review`, `judge`, `agreement`.
- **Views and gate:** `view`, `view-html` (snapshot, escaping, no scripts or network), `gate`.

These prove the evaluator's mechanics with stand-in models. They do not prove behavior with real models, which only runs prove.

`.skill-eval/review-work/tests/check-brief.test.mjs`, run by `npm run test:review-work`, checks in throwaway Git repositories that `check-brief.mjs` accepts a complete brief and refuses missing lines, paths and commits that do not exist, pasted text where a pointer belongs, a range that is not one, Review 2 or 3 without the previous report, and a report folder that does not exist. They prove what the script refuses, not that a brief points to the right inputs.

`.skill-eval/review-work/tests/review-packet.test.mjs` checks that `review-packet.mjs` fills a brief `check-brief.mjs` accepts, leaves the Boundary empty so it refuses, takes Review 2's diff from the previous brief, and names the gate triggers.

`.skill-eval/verify-work/tests/test-changes.test.mjs`, run by `npm run test:verify-work`, builds throwaway Git repositories and checks what `test-changes.mjs` lists and leaves out per kind, including a shared fixture edited to make a broken function's tests pass, head refs, patterns, paths with spaces, and errors. They prove what the script lists, not how agents use it.

## Limits

- A group runs on one host, so a question comparing Pi with Claude Code is two groups, not two arms.
- On Claude Code: bash only in a container, no `run_command`, Pi extensions or Freeflow, and retries at Claude Code's own default; its identity line and environment note cannot be removed, only recorded, and the note reports a Git repository above the workspace (Claude Code finds it itself, ignoring `GIT_CEILING_DIRECTORIES`).
- The Gondolin shell is tested only with fakes and skipped cases; it has not run on a real VM. Containers have: on 2026-10-19 the V0 to V3 groups, V2 and the pstack trial ran container subjects and graders on the real Colima engine (Docker 29.2.1, digest-pinned images), and a no-model check with the V0 image showed the probes holding, a skill's script running by its path, the network and the login path unreachable, and a grader in a fresh container. Until 2026-10-21 a container subject's `bash` started at `workdir` while its host reported the workspace's host path, so an absolute path from one failed in the other; container runs before then carry that distortion, seen in some V0, V1, V2 and Phase B runs as failed edits on `/testbed` paths and work moved into bash. On 2026-10-21 a no-model check with a `freeflow-vs-plain` image showed a file written on the host read back in the container at its host path and at `/testbed`, a file written in the container read on the host, `git add` working from a subfolder, and all six probes holding. On 2026-10-22 `tool-execution-container.test.mjs` ran on Colima (Docker 29.2.1, Ubuntu 24.04 image) with Pi 1.3.0: a background command's output read from the container and with `read`, its process gone from the container after `stop_background` (and still running there without the lifetime wrapper), a patch inside the workspace applied and one outside refused, monitor lines delivered, and an exit notice between prompts recorded in the turn before it.
- A task copy never has Git history, and a definition cannot ask for it: putting `.git` in the workspace would put Git's internals into the workspace fingerprints and changed paths. Ignored files in a fixture are copied but make a run non-canonical. `check-tasks` reports both.
- Network policy is `none` or `host`; a named allowlist of hosts is not supported. On `host`, declared commands and graders can read the user's files, including the provider login on disk.
- A pipeline stage cannot have its own configuration: every stage uses the arm's.
- Each rubric judge answers all dimensions in one call, so answers to one dimension can influence another.
- The only decision method is the sign test; there are no confidence intervals on rates.
- A turn's workspace snapshot is taken when its prompt settles; a run a notice starts afterwards joins that turn's transcript but not its snapshot. A command the guard routes into a container runs its own process group there only when the image has `setsid`; without it, only the command's shell is killed when the client stops.
- The standing suite measures first tries only: cost to a correct result after follow-ups needs command graders that run after each turn and a simulated user who sees what a user would see, which the evaluator lacks. An `ask_user` dialog cannot be answered in a run.
- A pinned Pi binary and mocks with record and replay do not exist.
- The gate suites are small (2 to 7 groups, one trial) and catch clear regressions only. A gate arm whose base commit predates a skill's path is invalid: `skills/evaluate-behavior` does not exist on `main` before the rename.
- The coverage matrix (`.skill-eval/coverage-matrix.json`) lists every skill as `unverified`; it records design coverage and source hashes, not behavioral evidence.
- Review Work's detection of a requirement enforced on one path and broken on another is weak on Haiku, and the review suite's known-issue comparison rests on five changes.
- A saved recipe does not make a live check cheaper. V2 (`.skill-eval/verify-work-v2/`) measured the next check with a recipe at about twice the cost of one from scratch on a one-file CLI, and about the same (median $0.41 against $0.35) on a 15-module service, plus $1 to $1.50 once to write the recipe; success was equal. What the recipe adds is consistent, rerunnable steps and drift checks (V1), not lower cost.
