# Track Work

> **Covers:** `skills/track-work/`
> **Tests:** `.skill-eval/track-work/`
> **Verified at:** `2f751259` (2026-11-14)

For anyone changing Track Work: what it is meant to change, why it is shaped the way it is, and what the evidence shows. The method itself is in [the skill](../../skills/track-work/SKILL.md); this record holds the reasons it does not. How its script keeps the store and the task folder is [Freeflow store and Schema 5 tasks](../subsystems/freeflow-store.md). It was started with the Schema 5 rewrite (task-004's Phase 7.1), so it records that rewrite's reasons in full and older choices only where they still shape the text. Task-004's design, with every choice and the owner's words, is its Spec (`memory-and-delegation.md` in that task's folder); the choices are cited here by its IDs (P1 to P81, T1 to T28).

## Purpose

Track Work keeps one task's memory so a fresh context, after a compaction, in another session or on another machine, continues the work without the conversation that produced it. Its reader is the agent doing the work, and it is read whole at every recovery, beside Discuss Work and Execute Work. It changes the decisions where memory is made or used: which task a session works on, what goes where in the record, when and how to checkpoint, and how to recover.

## Behavioral Claim

- **Behavior it produces:** the session takes only the task the user's message points to and writes only that one; the agreement is written in the user's words; a Slice is recorded before its first effect, with one-line updates pointing to their evidence; the record stays within a recovery budget the agent knows before writing; at Freeflow's notice the agent works on to a safe point, brings Current Context up to date where it no longer matches the state, rewrites In flight, saves the discussion that shaped the work, runs `checkpoint` and ends its turn; after a compaction it continues from the bundle without reading it again, and elsewhere recovers through `view recover` and the sources it names.
- **Failure it prevents:** from task-001 and the four Schema 4 records it was built from (Spec section 1; Schema 4 is read only by `migrate` now): records that grow and go stale (one Slice with 45 updates, a decision list of 7,600 words, recovery reading about 60,000), structure never used, Current Context patched instead of rewritten, records lost with a cloud container, and delegated work with no owner. From the evals of Pi's former Task Memory: an agent with a record in focus did the record's next action instead of the user's request 3 times out of 3.
- **Earliest decision:** a session's first message, where Freeflow's menu lists the project's tasks and the user's words decide which one, if any, is taken.
- **Cues before the body is read:** its description; core's cycle, which names Track Work when work spans sessions or a compaction, before pausing or transferring it, or when the user asks; on Claude Code the mod's menu, its notice and the bundle's opening and recovery lines, all printed by the script.
- **Guaranteed context:** the description on every host. Where Freeflow's mod runs, the bundle carries the skill whole into every new context cycle, which is why its length matters.
- **Nearby cases it leaves alone:** a question or a short self-contained result, which needs no task; Schema 4 records, which only `migrate` reads now; the decision list's method, which is Discuss Work's; delegation, which is Execute Work's reference.
- **When it stops steering:** at the task's close or release; between boundaries it asks for nothing ("update at boundaries, not after every step").

## Design

- **Schema 5 in the body, Schema 4 only for `migrate`** (P70). Pi's former Task Memory, its compaction summaries and its projects all rested on Schema 4 until Pi moved onto the store (step 3). A record made before Schema 5 is converted by `migrate`, the only command that reads Schema 4 (P73). The body describes one schema, so a Claude Code or Codex agent reads no Schema 4 method; `references/schema-4.md`, which held Schema 4's differences, its format and its projects and child records, was removed with Schema 4's commands, and the capability skill that linked into it went with Pi's Task Memory.
- **"Checkpoint" means only the save** (P71). Schema 4's Checkpoint, a selected stop on the route, became the agreement's `Back at` line, since both the user and the mod use "checkpoint" for the save before a compaction. Other skills still say "selected Checkpoint" until task-004's Slice 7.2 rewords them; the body's agreement section carries a one-line guard for that interval.
- **Rules kept few.** The Rules hold what is wrong in every case: the record is not authority (with the sharper wording Pi's former Task Memory used, that a record's next action is not a request, because of the 3-in-3 eval failure), taking and creating tasks only on the user's word, one writer, a Slice before effects, the script for lifecycle changes, the user's words for the agreement, recovery before action, the two evidence rules, and no secrets or private payloads in the task folder or a brief (restored when the handoff reference was removed, since the store syncs to a remote). Choosing a task, the budget, the checkpoint and recovery are judgment with goals, since each has cases where the default is wrong.
- **The checkpoint as a numbered method.** It is the one sequence that must happen in order at a moment of pressure (the notice), so it is steps, with In flight's labels spelled as `checkpoint --input` takes them. The safe point is Pi's compaction skill's definition, kept because it worked there; the mod's notice uses the same words (P50).
- **What goes where as one table.** Schema 5 has more places than Schema 4 had (agreement, decisions, Slice updates, delegations, Recovery's three classes of source, Space, In flight, discussion blocks), and the table is where an agent decides; Current Context's rule, that it changes only at a checkpoint (P5), follows it.
- **The store, projects and holds in the format reference** (2026-10-30, the owner's choice). They were a reference of their own; they are read with the task folder's shape often enough, and the two linked each other, so they merged. The file keeps its name, since Review Work and the developer docs link to it.
- **Choosing a task borrows the request table of Pi's former Task Memory, improved:** one row per thing the user's message can do, each with the script command, and the takeover, switch and close cases the hold adds (P40 to P44).
- **A resumed session's task comes back without a word from the text** (F36, 2026-11-03). The harness layer takes back a task the session's end released, and the menu says so in one line, so the menu paragraph only says when it happens; `checkpoint`'s refusal names `task take`, so the text adds no rule for it (Prefer A Capability To Prose).
- **Harness-neutral, with the harness layer named once** (2026-10-30, P74). The script, the record and the checkpoint work on any harness; the text names "Freeflow's harness layer" for what calls the script at the right moments (the menu, the notice, the sync, and, where the harness allows it, Freeflow's own compaction), and Claude Code's mod only as today's example. The notice and the checkpoint are the core; Freeflow's own compaction is optional, since Codex's hooks, for one, can only stop a compaction.
- **A task may belong to no project** (2026-10-30, P76). It lives in the store's `tasks/` with ID `task-NNN`, and `task move` puts it into a project or takes it out, so a first task needs no project first. The agent asks one question, through the harness's question tool where it has one, with the project choice in it (P75), as Pi's former Task Memory asked before creating a record, so the user always knows whether a task was made.
- **Context cycles as the measure of when memory is needed** (P77). "Spans several steps, compactions or sessions" left the agent no way to judge early; a context cycle, from a session's start or a compaction to the next compaction or the session's end, is defined once in the body, and a task is worth keeping when the work will outlast it. The harness layer's rows and notice name the context cycle, as Pi's status does.
- **"Context cycle" is Track Work's term, not core's** (P82, from Write Skill's Shared Terms procedure). Its readers are Track Work, Execute Work's context line and texts read where they appear (the notice, the rows, `estimate`'s output); Execute Work says it in plain words, and those texts name it in full, so no reader needs it before Track Work is read, and core pays nothing for it on every request. It is always written in full because core already calls agree, build, verify and review a cycle.
- **The context, measured** (P78, P80). `estimate` gives the context's use against the window and the notice point, and with the parts done and left, whether the rest fits or how many more cycles it needs, so the agent can tell whether work will outlast this cycle and plan where each cycle ends; the use comes from `--used` on any harness, or from the transcript where a reader knows its format. Where a harness layer runs, rows at 50%, 60% and 70% show the context passively; they are appended, so the prompt cache holds, and only at those marks, since every row stays in the conversation. Execute Work points to `estimate` when the route is set (P79).
- **What work used, measured by the script** (task-004's Spec, section 12, P83, P89, T29 to T31). `slice start` takes a Slice's first reading, each `checkpoint` adds what was used since the last one (so a Slice across compactions or sessions is counted whole), and `slice close` takes its last, into a `Measured:` line the History entry keeps ("not measured" when nothing could be read): the context it added per context cycle, its billed tokens and list-price cost by model and effort, and its working and wall-clock time (`lib/measure5.mjs`). Readings come from the transcript the harness layer names (`FREEFLOW_TRANSCRIPT`) or `--transcript`, else `--used`, never from a lookup of their own, so a test never reads the session that runs it. The harness layer names the transcript (on Claude Code the mod, at session start), and Track Work's suite runs with it cleared (`scripts/validation/with-symlinked-tmp.mjs`), since a test that inherited it measured the session running it and broke the pinned Slice outputs. `delegate close` measures a worker the same way from its own log beside the coordinator's transcript, found by the brief's Handle or the mod's map of workers, so its History entry needs no typed tokens or minutes (A).
- **Store setup lives in Setup Freeflow** (2026-10-30, P91, P72 changed). Track Work keeps only the trigger: a task always lives in the store, and where none exists the agent asks once, local only or local + cloud, then follows Setup Freeflow's `references/store-setup.md`, which also moves older records in (a repository's `.freeflow/tasks/` and Pi's former Task Memory, through `migrate --project`) and ends with `session status`'s `missing` list empty. Setup is read once per user and machine, so it does not belong in a skill read on every task; Setup Freeflow already owned the store's setup section.
- **Freeflow compacts only on the agent's request** (2026-10-30, P102). `checkpoint --compact` is the one trigger; the notice reminds. First the mod compacted after any checkpoint that followed its notice (P51, T12), so a checkpoint taken for a pause or a switch after the notice also threw the conversation away, and the agent could not compact earlier at a natural boundary. Rejected: every checkpoint compacts (a pause or a switch would compact too).
- **Planning from measured cost** (P84 to P90). `slice start` also records a prediction (`Predicted:`): the median context, working time and cost of the nearest pool holding 3 measured Slices (the task, its project, the store; partly measured ones left out), each scaled by the median of actual over the uncorrected prediction from the nearest pool holding 3 predictions with their actual; History keeps it beside `Measured:`, so later predictions correct themselves (`lib/planner5.mjs`). `estimate --plan` lays the Slices left (Future Work, or a list given) across context cycles at that size, flags any bigger than one, lists those with no dependency between them, prices delegations by kind, model and effort, and a fan-out, and counts how many of each kind, check and model were sent back and why (SPEC-010 4.2); before 3 Slices are measured anywhere it plans at this context cycle's rate, from `--done`. Its `--json` feeds Discuss Work's agreement (`choices.mjs agreement --plan`): a Size line and, in Technical, the plan (P87). `estimate --project` and `--store` add up measured use (B). Medians, ranges and ratios only, no fitted model: a task holds too few Slices for one, and each figure can be traced to the entries it came from (rejected: a probabilistic predictor). Slices have no kind, so all of a task's Slices size its next ones (P88). Track Work owns the planner, since its figures are the record's and History's (P90); each skill that decides with them has one pointer where D-002's map found the decision: Execute Work's delegation reference beside its pointer to the routing table and at fan-outs, the worth-keeping paragraph and the rolling route here, Review Work's choice of tier, Evaluate Behavior and Research Work before a paid run, and Discuss Work's agreement; core has none, by P82's reasoning.
- **Sized Slices** (2026-10-30, A-004 P13 to P18). The planner's first prediction for #136 was a third of what it used, and its plan for the rest of step 3 gave every Slice the same size: the median Slice cannot tell a one-line fix from a 200-file removal, and a reading that found no requests (S-029's 0, F31) pulled the median down. A Slice now carries `Size: <n> files` (the files it will add or change; a deletion costs almost nothing, so it does not count), `slice start` records `Base` (the work repository and its commit) and `slice close` writes `Files` (added, changed or renamed from Base to HEAD); `slice size` gives the Slices closed before this their Files, dated. A sized Slice is predicted as its size times the median per-file rate of the nearest pool with 3 sized Slices, with the range from the lowest and highest rate; the correction now starts from the first actual, as the geometric mean pulled toward 1 by two on-target Slices, and corrects each kind of prediction only by its own kind; a zero reading is not measured; and the plan leads with its range and what it rests on. Still a ratio, not a fitted line: with four sized Slices a robust line (Theil–Sen) gave a negative intercept (rejected), and every figure stays traceable to its entries.
- **A Slice's cost by its model and effort** (2026-11-03, A-005 P8). The cost of a Slice on Haiku is a small share of the same Slice on Opus, so a median over every model priced a Haiku Slice at Opus prices. Its cost now comes from the pool's Slices run mostly on the model and effort it starts on (the transcript's newest request, as `modelNow()` reads it) once 3 were, else from all of them, and the Predicted line says which (`cost from the <n> run on …`, `cost measured mostly on …`); context and working time stay pooled over every model, since the work, not the model, sets them. A prediction whose cost came from another model than its Slice ran on no longer corrects later costs, or one Haiku Slice priced at Opus would pull every later cost down. With `--used` no model is known, and the cost is the all-model median.
- **The cost governor's lines in the event log** (2026-11-03, SPEC-014). Claude Code's mod governs cost against the plan's usage windows and a held task's predicted range, which it reads from `estimate --plan --json` (its `total.usdHigh`); each row or notice it gives is a `governor` line (`cap`, `unit`, `limit`, `use`, `response`), and `events summary` lists them, so what the governor did is measured where the session's other events are. Track Work keeps the line's schema and the planner; the mod keeps the caps and their wording.
- **The task folder in the checks** (2026-10-30, F29). The record names its files relative to its task folder, and a compacted agent had to work the folder out from the store, the project and the task ID; the checks that `view recover` and the bundle share now open with its path.
- **The session's newest log** (2026-10-30, F31). A session resumed in another folder gets a second Claude Code log there, and only the newest grows, so the measure reads the newest copy (`claudeCodeLog()`); before, it took whichever folder was listed first and measured nothing.
- **Pointers into the repositories in Space** (2026-10-30, F34). Since the store moved records out of the repositories they change, a record's pointer to a repository file, such as a skill or `AGENTS.md`, resolved only when the command ran inside that repository; a cloud session started in its home folder got a bundle without four sources the record listed, and the checks called three of them missing. A relative pointer now falls back to each repository Space names, where `local/repositories.json` says it is, and an entry recovery reads always (Defined by or Read on recovery then, an always Recovery line now) that names no pointer gets a check line, since recovery never reads it for the agent.
- **Pi's session read by the script** (2026-10-30, P2, P4). Pi moved onto the store and the bundle, so `discussion list` reads Pi's session file too, along its active branch. A session summary asks for Freeflow's compaction (where the session's driver claims `compact` in its `capabilities.json`; elsewhere `--compact` leaves no request and says so) and shows in `session status` with no store, since both live in the Freeflow home's `sessions/` folder: Pi users with no store keep Freeflow's compaction. Pi's own result index (`r12`) went with Pi's result carry, and the script reads no tool results either (Carry is files only, 2026-11-03).
- **The rules at session start** (2026-10-30). The Spec reads the store's and the project's `rules/` at session start, but the menu carried none, so a session saw them only once it took a task and recovered it. `task here --rules` prints them after the menu, from the script, so every harness layer gives them the same way; the plain `task here` an agent runs mid-session leaves them out, since they are already in its context.
- **The routing table is the user's file, read by the script** (SPEC-010, 2026-11-04). A worker's model and effort come from `rules/routing.md` in the store, a project's own first, which `routing5.mjs` parses and `delegate open` reads, so the choice is recorded on the brief (Settled, Check, Route) and in History with a sent-back reason, and the planner can tell a bad brief from a weak model. The table sits in `rules/` because rules are already read whole at every recovery and only the user edits them; `store init` writes the default, two tiers and no Sonnet (P1). Learning the table from the rates is left for later.
- **Carry is files only** (2026-11-03, A-004). A Carry line once named a tool result too, numbered by `carry list` and pinned to its tool-use ID, and the bundle added the context cycle's newest tool results within a carry budget, as Pi's context reuse does. It was removed before any release. Carry is for the items the agent would otherwise read again after a compaction, chosen before it and copied fresh into the bundle; what a result showed goes into In flight's `Observed:` line, and a list of every result is one more thing the agent has to choose from and keep track of. Hassan: "I don't want tool results" (2026-11-03). A session summary's Carry lines name files the same way, and its bundle copies them.
- **One Recovery list** (2026-11-03, A-005 P4 to P7, P28 of A-004). Defined by, Read on recovery, Read when and In flight's Carry line were four places for one thing, what recovery reads, and `view recover` told the agent to read the first two but not the Carry files. They are one Recovery section, each line naming its class: `always` (counted), `always, not counted` (accepted definitions and the skills the work follows), or `when <trigger>`; any file may take `(lines a–b)`, as a Carry line could. The list is decided at each checkpoint and kept unless changed, and it can be empty: Hassan, "if recovery means recovering state then shouldn't all of it be under recovery?" and "keep unless changed, and you should also be able to have an option to carry nothing" (2026-11-03). The checkpoint prints each line's size and share of the budget, and names a dropped definition, so dropping one is never silent. The old headings are refused, not converted, since no release wrote them. The session summary takes the same section (P9 of A-005, a default), so a summary and a record speak one vocabulary.
- **Recovery has two paths.** After Freeflow's compaction the bundle is the conversation, so the text says not to read it again; elsewhere `view recover` and the reads it lists. The fallback (a compaction before the checkpoint) gets its own line because there the record is behind the summary (P16).

- **The record changes when something settles** (discussion block B-024, 2026-11-10). What happened is recorded when it happens: a stop or a limit, a Slice started, a worker started or its return accepted or sent back, a commit, a file or a sent message. None of it can be worked out again. What the agent currently understands is recorded once, at the checkpoint, since it keeps moving until then. Current Context is brought up to date only where a line no longer matches the state, because each rewrite of a true line risks changing what it means.
- **The agreement holds terms only** (B-024). Its lines are what the agent may do, what it may not, where it stops and where it comes back; a message that changes none of them belongs in the discussion blocks, and a new outcome gets a new agreement rather than more lines.

## Rejected

- **Current Context rewritten whole at each checkpoint.** Each rewrite of a line that is still true risks changing what it means, so only the lines that no longer match the state are rewritten (B-024).
- **Every change to the agreement recorded at once.** An agreement whose later lines undo its earlier ones has to be replayed to learn what holds, so a change to the terms is written when it settles and a different outcome opens the next agreement (B-024).
- **Schema 5 only, with Pi's guidance left until step 3.** A Pi user who updated Freeflow would get Track Work text that no longer matched their records (P70).
- **Keeping "Checkpoint" for both meanings.** The save and the selected stop would share one word in the same skill, and the save is the one the notice uses (P71).
- **A Schema 5 record in the repository when no store exists.** Without a store nothing syncs and the mod stays off. First the repository's ignored folder was the fallback when the user declined the store; since P72 changed (2026-10-30), a task always lives in the store, set up local only or local + cloud, and a user who wants neither gets no task.
- **A separate reference for workers.** The delegation reference holds the worker's side (P36).

## Dropped

- **Accepting a plain bullet in Future Work.** The live run's agent wrote one and was refused; the refusal now names the shape instead, since Future Work holds only proposed Slices and the fixed budget counts them (T21).
- **Repeating Pi's "compact now" notice on Claude Code.** Claude's own compaction, with the bundle after its summary, is the backstop, and a second notice would turn the soft one into a hard one (P50).
