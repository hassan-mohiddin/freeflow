# F2 on Haiku: how often a correct change is rejected

Run on 2026-10-12 at suite commit `8494751c`: the 15 clean variants the clean audit kept (`clean-audit.json`), requirements given as declared context, 3 independent trials each, 45 reviews. Review Work from the working tree; subject `anthropic/claude-haiku-5-5` (thinking medium) with `@gotgenes/pi-anthropic-auth@3.4.2`. Each reviewer had `read`, `write`, `ls`, `find` and a `tests` command that runs the change's declared tests on its full tree. Result IDs are in `f2-runs.tsv` beside this note.

A review rejects a correct change when it ends Inconclusive or Blocking: both stop the change. Pass and Non-blocking let it proceed (Review Work: Non-blocking permits it with explicit deferrals), and several kept changes have small genuine non-blocking issues.

## Why the 14 rejections happened

Read from each review's deciding findings:

- **Harness faults, 3.** One test (`notices.test.js`, "under projection the Coordinator is warned by the full history") failed under load in one reviewer's run; it is now skipped in this environment for every case that runs it. Two requirements, narrowed earlier in the audit, depended on code the fixture does not hold (`rs-24c53d4b` requirement 3 on `entryIdFromContextRef`, `rs-e312562f` requirement 5 on `observe()`'s caller); both are now narrowed to what the fixture shows.
- **The reviewer's own evidence ignored, 3** (`rs-97b149b0`, every trial). The reviewer ran the declared tests, which cover the edited notice tests and passed, and still withheld Pass because the author's report says the author did not rerun them, or did not run `npm run check`.
- **A missing test for a requirement the code visibly meets, about 6.** For example `rs-ccfe0bef` requirement 4 (an unresolvable shell reports `unavailable`) and `rs-9849a16c` requirement 3: the reviewer reads the implementation, finds no test for it, and reports Needs evidence.
- **Genuine open questions, about 2.** `rs-92d1d78d`'s test accepts either Pi's refusal or Freeflow's, which the clean audit also noted; `rs-9849a16c`'s ordering of a user-input suspension and a recovery is a gap the audit narrowed out of the requirement but a careful reviewer may still raise.

## What it means for Review Work

The two middle groups are Review Work behaviour, not suite faults, and together they are most of the remaining rejections. Review Work already says to establish that a stronger claim is required before asking for evidence, and that a missing result is not itself a defect. Haiku still treats "the author did not run X" as Needs evidence after running X itself, and treats a missing test as Needs evidence when the behaviour is readable in the code. Candidate wording to measure (not applied):

- When you have run a check yourself, judge from your result; the author's not running it is not Needs evidence.
- A requirement the code visibly meets, with no test for it, is a test-coverage Non-blocking Issue, unless the behaviour cannot be confirmed by reading.

Any such change must be measured on the whole suite, so the false-rejection gain is weighed against defect detection on the seeded and real variants.

## Limits

- Haiku only, one model as subject; judgments read from the first line, the rejection reasons classified by reading the reviews, not by a second reviewer.
- 15 changes and 3 trials; per-change rates are coarse.
- The first F2 run of the day (45 reviews, before the runner fixes in `8494751c`) is not used: its runner printed a misleading build status, cut long test output past the tool's cap, and ran tests under overload.
