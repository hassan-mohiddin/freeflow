We have been brainstorming a Pi + cmux pane delegation harness for Freeflow.

Settled so far:
- All visible child panes will run Pi.
- Use cmux only for pane management; do not add tmux.
- The harness should expose Pi tools first, not a human CLI first.
- The orchestrator should keep a saved Pi session; child pane evidence is stored by the harness.
- Internal state should be JSON/JSONL, but model-visible result/input can use a compact line protocol.

Still not deeply discussed:
- how role-specific context profiles are loaded into child Pi panes;
- which tools are active for each role and how enforcement works;
- exact FFRESULT/result parsing and failure/timeout behavior;
- output-router bridge boundaries;
- how worktrees enter execution workers later.

Should we write the spec now?
